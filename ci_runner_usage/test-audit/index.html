Axis 2 · Audit for unnecessary or unrealistic tests

Plan · Nov 3, 2026 · Tests that cost runner time but give little signal. Every item was checked against main, CI data and, where it mattered, Spyre hardware. Making the remaining tests faster is axis 1.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

The audit covers all of tests/, measured against one cold integration run: 2,563 cases, 448 pytest-min. The ~2,100 cases that take under a second add up to about a minute, so it concentrates on the slow ones.

These minutes don't overlap with axis 1. Each test is acted on by only one of the two pages. They're cold-run minutes; on our own warm PR runs the same tests cost 4–10× less (cold vs warm). Items that turned out not to be worth doing are at the bottom.

Where "out of the integration tier" goes: the marker design is on axis 3. The integration tier runs only an opt-in e2e_smoke set, regression is integration plus regression_extra, and trunk runs everything. On this page, "out of the integration tier" means the test doesn't get e2e_smoke. "Trunk-only" means it doesn't get regression_extra either.

The common con, and how to handle it: almost every demotion means a bug surfaces after merge instead of before. Three things keep that acceptable.

  • A trunk-failure alert. It doesn't exist yet; it's a small addition, since Slack is already wired through pr_reminder_slack.yaml.
  • Any PR can opt in to the full set today by dispatching integration-tests.yaml with test_type=trunk on its ref.
  • A rule: demote a test only when something cheaper keeps covering the same code path per PR.

Nightly items also need a new scheduled workflow. Today the only crons are cleanup and reminders.

A · Expected failures and stale markers

A1 · e2e/test_kernel_cache.py::test_kernel_cache[tp1-fresh]

Nightly6.9 min cold · 7.5 min warm (costliest case in a PR run)

Evidence: this is a strict xfail(raises=CacheGrewError) for a known cross-process cache-key bug: the fused RMSNorm+mm and attention keys differ between processes. No issue is linked. It still builds a cold and a warm engine on every run, and it's the single most expensive case in a warm PR run.

Change: add pytest.mark.nightly to the param, and link a new issue in the xfail reason.

ProsAbout 7 min off every tier, warm or cold.
ConsA fix is noticed only if somebody watches nightly. It's also the test that the compile-cache axis depends on.
Recommended
  • Action: move it to nightly and file the issue now.
  • Overcoming the cons: keep strict=True. Once the bug is fixed, nightly fails with XPASS, which forces the marker off. Assign the issue to the compile-cache owner, since fixing it unblocks cross-run cache hits.

A2 · Probes whose linked issue has closed

Validated on hardwareRe-link, don't deleteprobe tier

Evidence: in tests/probes/test_spyre_fallback_probes.py, the xfail on test_spyre_lm_head_unpadded_matmul_and_slice tracks #1918, which is closed. The probe tracking the open #3499 also cites #3502 and #3503, both closed. On hardware, both still fail (XFAIL). The bugs are real; only the issue links are stale.

Change: point each reason at a new open torch-spyre issue that describes the current failure.

ProsThe probe tier tracks live issues again, and each probe flags its fix with an XPASS.
ConsAs more issues close, links will go stale again.
Recommended
  • Action: re-link both, and keep the probes.
  • Overcoming the cons: add a small CPU-only check on ubuntu-latest. It reads issue numbers from xfail(reason=…) only, not from comments, treats a bare #N as torch-spyre, and flags any that are closed.

D · Duplicates of upstream vLLM tests

D1 · e2e/test_transformers_backend.py::test_transformers_matches_native

Drop the micro-g3.3 case~7 of 14.3 min

Evidence: upstream_tests.yaml runs upstream tests/models/transformers/test_backend.py::test_models as mandatory_pass on the same two models. The Llama-3.2-1B case (head_dim 64) takes our padded-head path; micro-g3.3 (head_dim 128) doesn't.

ProsRemoves duplicate work.
ConsUpstream tests run only in regression and trunk, so dispatched runs lose the micro-g3.3 generation check.
Recommended
  • Action: drop only the micro-g3.3 case. Keep Llama-3.2-1B, which tests the Spyre-specific padding.
  • Overcoming the cons: test_transformers_backend_compile (3.3 min) still covers the backend on every PR, and micro-g3.3 still generates there through test_compile.

E · Unrealistic or niche configs

E1 · test_vllm_spyre_next::test_long_context_model_load

Trunk-only2.5 min

Evidence: max_model_len=131072, eager, generating 32 tokens of "Hello World". All it really proves is that the config is honoured. The engine build is most of the cost, so dropping generate alone would save little.

ProsThe whole case leaves per-PR runs.
ConsA long-context config regression is caught only after merge.
Recommended
  • Action: make it trunk-only, unchanged.
  • Overcoming the cons: add a CPU-only check on every PR that builds EngineArgs(max_model_len=131072, …).create_engine_config() and asserts model_config.max_model_len. It needs no device and no engine.

E2 · test_compile::test_whole_model_granularity

Trunk-only6.0 min

Evidence: SPYRE_COMPILE_GRANULARITY=model is a non-default debug switch.

ProsNo coverage of the default path is lost.
ConsA torch-spyre change could break this switch unnoticed until trunk runs.
Recommended
  • Action: demote it.
  • Overcoming the cons: on PRs that touch the compile path, opt in with the test_type=trunk dispatch. A break that comes from torch-spyre shows up at the next trunk run and goes to the trunk alert.

E3 · TP2 parity at full size: test_tp2_compiled_image_prompt_matches_tp1 (14B) and the gemma-4-26B row

Validated on hardwareOut of the integration tier47 + 27.2 min

Evidence: both compile a full model twice (TP1 and TP2). They are the two most expensive tests in the tier, and the image test is its longest leg. On hardware, cutting layers from the 14B or the 26B fails to load: vLLM still loads every checkpoint layer. That rules out a truncated per-PR version. The gemma-4 row's per-PR replacement is a nano model, which passes TP1-vs-TP2 parity in 12.5 min (axis 1 E3).

ProsAbout 74 min off every integration run, including its longest leg.
ConsTP2 vision bugs, such as all-reduce in the vision tower, show up after merge instead of before.
Recommended
  • Action: keep both in regression (regression_extra), and replace the gemma-4 row in the integration tier with the nano version.
  • Overcoming the cons: per PR, the nano gemma-4 and micro-g3.3 TP2 parity cases keep the decoder's TP all-reduce covered, and our own PRs still run the image test in regression. If nano's vision tower starts compiling on a newer torch-spyre (see axis 1, dropped), a nano image-parity case can return to the integration tier.

F · Oversized parametrize grids

F1 · custom_ops/test_mlp.py

Shrink3.0 → ~1 min

Change: today it's 4 functions × 24 shapes (96 cases). Reduce the {tokens, heads, kv_heads, head_size, bias} grid pairwise, to about 8 cases per function.

ProsPairwise coverage still catches most interaction bugs.
ConsA bug that only appears with three particular factor values together could slip through.
Recommended
  • Action: shrink it, and always keep the shapes of the models we serve (micro-g3.3, gemma-3, gemma-4) as explicit rows.
  • Overcoming the cons: run the full grid nightly.

Rollout

  1. Infrastructure: the e2e_smoke / regression_extra markers (axis 3), a nightly marker with its cron workflow, and the Slack trunk-failure alert.
  2. No-loss PR: A1, B, C2, C3, D1, E1 (with its CPU config check), E2 and F1. About 65 min per integration run.
  3. Paired with axis 1: C1 and E3 land together with axis 1 E3 (nano gemma-4), so each demotion comes with its per-PR replacement. About 98 min.
  4. Probe hygiene: A2 re-links, and the closed-issue checker.
  5. Ongoing: once a quarter, query ClickHouse for slow tests that haven't failed in 30+ days.
