Axis 2 · Audit for unnecessary or unrealistic tests

Plan · Nov 3, 2026 · Tests that cost runner time but give little signal. Making the remaining tests faster is axis 1; the two pages share one set of decisions.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

The audit covers all of tests/, measured against one integration run's JUnit data: 2,563 cases, 448 pytest-min. The ~2,100 cases that take under a second add up to about a minute, so it concentrates on the slow ones. Probe, quality, attention and upstream tiers aren't in that run, so their minutes show as "—".

The 14B multimodal merge, the TP2 parity tests and the remaining gemma-4 compile row are no longer counted here. They stay in the integration tier and are made cheaper in axis 1, so the two pages never act on the same case. Combined, the two plans remove about 200–230 of 448 minutes. These are cold, dispatched-run minutes; on our own warm PR runs the same tests are 4–10× cheaper (see cold vs warm), but demotions save the same share either way.

Dropped after checking CI data: the token-major attention grid trim (the compiled token-major cases total about 2.6 min across 8 shards) and the gemma-4 MoE tp grid shrink (the tp2 width pads to a stick count that neither tp1 nor tp4 has, and the whole grid takes under a minute on PR runs). Details are in E and F.

Feasibility: every action here was checked against main (593b5709), and every linked issue's state against GitHub. One earlier item, a stale fp16 exp probe, was dropped because the probe no longer exists on main. Items that still need a hardware run say so, and that run happens in the item's own PR.

Prerequisite (checked against main): register trunk_only and nightly in pyproject.toml. Today every test type uses the same hard-coded smoke expression in the Makefile, and trunk differs only in which matrix entries run. So the smoke and distributed shard targets have to append and not trunk_only and not nightly when TEST_TYPE is integration or regression. Design this together with R1's integration_heavy on axis 3.

Two pieces don't exist yet and must be built first: a scheduled workflow that dispatches integration-tests.yaml nightly (today the only crons are cleanup and reminders), and a trunk-failure alert. Slack is already wired up through pr_reminder_slack.yaml, so the alert is small to add.

The common con, and how to handle it: almost every demotion means a bug surfaces after merge instead of before. Three things make that acceptable. The trunk alert notifies someone, who fixes the break before the next release cut. A PR can opt back in today by dispatching integration-tests.yaml with test_type=trunk on its ref, which is an existing input; a new PR label could trigger the same thing, but it must not reuse integration-test, which hands testing to Jenkins. And the rule of thumb is to demote only when something cheaper stays per PR for the same code path.

A · Expected failures and stale markers

A1 · e2e/test_kernel_cache.py::test_kernel_cache[tp1-fresh]

Nightly6.9 min

Evidence: a strict xfail(raises=CacheGrewError) for a known cross-process cache-key bug (the fused RMSNorm+mm and attention keys differ). No issue is linked, and the test still builds a cold and a warm engine every run.

Change: add pytest.mark.nightly to the param, and link an issue in the xfail reason.

ProsSaves 7 min on every tier.
ConsThe fix is only noticed if somebody watches nightly. This is also the test the compile-cache axis depends on.
Recommended
  • Action: move it to nightly and file the issue now.
  • Overcoming the cons: keep strict=True, so the nightly run fails when the bug is fixed (XPASS), which forces the marker to be removed. Assign the issue to the compile-cache owner, since fixing it unblocks cross-run cache hits.

A2 · e2e/test_multimodal.py::test_gemma4_request_max_soft_tokens_replays_warmed_budgets

Trunk-only now, rewrite next~7 min warm · times out cold

Evidence: merged in #1376 with timeout(3600). On a cold compile cache, warmup alone runs past the limit: gemma-4-26B-A4B, six vision budgets on a 27-layer tower, and a 2048-length decoder. It timed out in job 126072048399 (PR #1467) and needed 58.5 min in dispatched run 41683563423. Warm runs pass in about 7 min. A cold cache follows every lockfile bump, which means every vLLM or torch-spyre upgrade PR, and most dispatched runs.

Change: add pytest.mark.trunk_only to the test as a stop-gap, then rewrite it per axis 1 E9: gemma-4 nano and budgets (280, 576, 1152).

ProsUpgrade PRs and dispatched runs stop failing on a timeout that says nothing about correctness.
ConsUntil E9 lands, a break in request-driven budget selection (#1376's feature) shows up only after merge. Trunk runs after a lockfile bump can still hit the timeout.
Recommended
  • Action: demote now and land E9 as the follow-up. That makes this a pair, like the other demotions.
  • Overcoming the cons:
    • Feature coverage gap: keep it short. E9 is a small change (model id and budget tuple), and once it lands the nano version goes back to per-PR.
    • Trunk timeout: until E9 lands, raise only this test's timeout to 5400 s at trunk, so the cold run there finishes instead of flaking.
    • Preventing a repeat: new multimodal e2e tests should start from a nano model and only the shapes their assertions use. Add a review-checklist line in docs/contributing/README.md, and say in the PR how long the test takes on a cold cache.

A3 · Probes whose linked issue has closed

Re-run onceprobe tier

Evidence: in tests/probes/test_spyre_fallback_probes.py, the xfail on test_spyre_lm_head_unpadded_matmul_and_slice tracks the closed #1918, and the probe tracking the open #3499 also cites the closed #3502 and #3503. The other xfails track open issues: #3798, #3851, #3508, #3507, #2971, #4032, #4403, #4404. Issue references mix torch-spyre#N and bare #N.

ProsKeeps the probe tier honest.
ConsNeeds a hardware run, and this will happen again as more issues close.
Recommended
  • Action: run the probe tier once. Delete any probe that now passes, and give any that still fails a new open issue.
  • Overcoming the cons:
    • Needs hardware: batch it with the next scheduled probe-tier run instead of a dedicated one.
    • It will happen again: add a small CPU-only check on ubuntu-latest that reads issue numbers from xfail(reason=…) only (not comments), treats a bare #N as torch-spyre, and flags closed issues. Then this never needs a manual audit again.

E · Unrealistic or niche configs

E1 · test_vllm_spyre_next::test_long_context_model_load

Trunk-only2.5 min

Evidence: max_model_len=131072, eager, and it generates 32 tokens of "Hello World". It's really only a check that the config is honoured. Building the engine dominates the cost: this case takes about as long as a 128-token engine build, so dropping generate alone would save very little.

ProsRemoves the whole case from per-PR runs.
ConsA config regression at long context is caught only after merge.
Recommended
  • Action: mark it trunk_only, unchanged.
  • Overcoming the cons: add a CPU-only per-PR check that builds the EngineArgs(max_model_len=131072, …).create_engine_config() and asserts model_config.max_model_len, with no device and no engine. That catches config regressions in seconds.

Trunk-only6.0 min

Evidence: SPYRE_COMPILE_GRANULARITY=model is a non-default debug switch.

ProsNo default-path coverage lost.
ConsA torch-spyre change can break this switch unnoticed until trunk runs.
Recommended

  • Overcoming the cons:

F · Oversized parametrize grids

F1 · models/test_gemma4_moe.py::test_persistent_matches_dense_reference

Dropped: every tp case is distinct~0.5 min warm

Evidence: here tp is a fixture parameter that divides the expert width (704) on one card. With 64-element fp16 sticks:

  • tp1: 704 = 11 sticks, no padding.
  • tp2: 352 = 5.5 sticks, padded to 6.
  • tp4: 176 = 2.75 sticks, padded to 3.

Each is a different padded shape, so none covers another. The 18 cases take about 0.5 min on a warm PR run. The 8.3 min in the dataset were cold compiles.

Recommended
  • Action: keep the grid. Its cost is compile time, which the compile-cache axis already removes on warm runs.
  • Overcoming the cons: not applicable, since nothing changes.

F2 · custom_ops/test_mlp.py

Shrink3.0 → ~1 min

Change: 4 functions × 24 shapes (96 cases). Reduce {tokens, heads, kv_heads, head_size, bias} pairwise to about 8 per function.

ProsPairwise coverage still catches most interaction bugs.
ConsA bug that needs three particular factor values together could slip through.
Recommended
  • Action: shrink it, and always include the shapes of models we serve (micro-g3.3, gemma-3, gemma-4) as explicit rows.
  • Overcoming the cons: run the full grid under nightly.

The CPU-only grids (test_shape_bucketer 105, test_spyre_attn_bucketer 185, mrv2/test_layout 112 cases) take under a second in total. Leave them as they are.
