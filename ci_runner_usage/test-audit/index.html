Summary

I audited all of tests/ against one integration run's JUnit data: 2,563 cases, 448 pytest-min. The ~2,100 cases that take under a second add up to about a minute, so the audit concentrates on the slow ones. Probe, quality, attention and upstream tiers aren't in that run, so their minutes are marked "—".

New marker needed: most actions demote a test rather than delete it. Register trunk_only (runs on push to main and in the merge queue) and nightly in pyproject.toml, and exclude them from the smoke and distributed MARK_EXPR in the Makefile for the integration and regression test types. This is the same mechanism as R1's integration_heavy, so the two should be one marker design (axis 3).

Lowest coverage cost: B, D, E2, E3 and E4. Needs agreement: C1 and D1, because they would leave torch-spyre's dispatched runs without gemma-4 and transformers-backend signal.

Rollout

  1. Land the marker. Register trunk_only and nightly and wire them into the Makefile selection. One small PR.
  2. Zero-coverage-loss PR: A1, B, C4, E2 and the F grid shrinks. About 50 min per integration run.
  3. Agreement PR: C1, D1, E3 and E4, together with the truncated replacements from axis 1 (E2, E3, E6), so dispatched runs keep a gemma-4 and TP signal.
  4. Probe hygiene: one probe-tier hardware run to settle A2 and A3.
  5. Ongoing: query ClickHouse JUnit history (from push-to-clickhouse.yaml) for slow tests that haven't failed in 30+ days, and review that list quarterly.
