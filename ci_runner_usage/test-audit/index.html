Axis 2 · Audit for unnecessary or unrealistic tests

Plan · Nov 3, 2026 · Tests that cost runner time but give little signal. Making the remaining tests faster is axis 1; the two pages share one set of decisions.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

The audit covers all of tests/, measured against one integration run's JUnit data: 2,563 cases, 448 pytest-min. The ~2,100 cases that take under a second add up to about a minute, so it concentrates on the slow ones. Probe, quality, attention and upstream tiers aren't in that run, so their minutes show as "—".

The 14B multimodal merge, the TP2 parity tests and the remaining gemma-4 compile row are no longer counted here. They stay in the integration tier and are made cheaper in axis 1, so the two pages never act on the same case. Combined, the two plans remove about 200–230 of 448 minutes.

Prerequisite: register trunk_only (runs on push to main and in the merge queue) and nightly in pyproject.toml, and exclude them from the smoke and distributed MARK_EXPR for the integration and regression test types. This is the same mechanism as R1's integration_heavy, so design them together on axis 3.

The common con, and how to handle it: almost every demotion means a bug surfaces after merge instead of before. Three things make that acceptable. Trunk failures must page someone and block the next release cut. A PR can opt back in with a label or a /spyre-test trunk comment. And the rule of thumb is to demote only when something cheaper stays per PR for the same code path.

A · Expected failures and stale markers

A1 · e2e/test_kernel_cache.py::test_kernel_cache[tp1-fresh]

Nightly6.9 min

Evidence: a strict xfail(raises=CacheGrewError) for a known cross-process cache-key bug (the fused RMSNorm+mm and attention keys differ). No issue is linked, and the test still builds a cold and a warm engine every run.

Change: add pytest.mark.nightly to the param, and link an issue in the xfail reason.

ProsSaves 7 min on every tier.
ConsThe fix is only noticed if somebody watches nightly. This is also the test the compile-cache axis depends on.
Recommended
  • Action: move it to nightly and file the issue now.
  • Mitigation: keep strict=True, so the nightly run fails when the bug is fixed (XPASS), which forces the marker to be removed. Assign the issue to the compile-cache owner, since fixing it unblocks cross-run cache hits.

A2 · probes/test_fp16_exp_underflow_probe.py

Retargetprobe tier

Evidence: torch-spyre#4517 closed on Sep 23. The reason text says "drop the xfails in test_kv_cache_determinism.py", but that file has none left. The probe is still a strict xfail, so the device's exp still floors.

ProsRemoves a tripwire that points at a closed issue.
ConsIf the hardware behaviour is real, deleting the probe loses the only guard on it.
Recommended
  • Action: retarget rather than delete. Rewrite the reason against a new open torch-spyre issue describing the current behaviour.
  • Mitigation: if torch-spyre says the behaviour is intended, turn the probe into a passing test that documents it, and delete the xfail.

A3 · Probes whose linked issue has closed

Re-run onceprobe tier

Evidence: test_spyre_lm_head_unpadded_matmul_and_slice (#1918) and the fp32 bmm probes (#1794) link closed issues. The other probes link open ones: #3798, #3851, #3508, #3507, #3499, #2971, #4032.

ProsKeeps the probe tier honest.
ConsNeeds a hardware run, and this will happen again as more issues close.
Recommended
  • Action: run the probe tier once. Delete any probe that now passes, and give any that still fails a new open issue.
  • Mitigation: add a small CI check, CPU-only on ubuntu-latest, that reads issue links from xfail reasons and flags closed ones, so this never needs a manual audit again.

C4 · test_vllm_spyre_next::test_basic_model_load

Delete2.2 min

Evidence: it asserts len(text) > 0 on eager micro-g3.3, which test_compile[micro-g3.3] already covers with an exact-output check.

The 14B multimodal "produces output" tests were a candidate here too (the old C2). They stay in the tier: axis 1 E1 merges them onto one engine and E5 adds dummy weights.

D · Duplicates of upstream vLLM tests

Evidence: upstream_tests.yaml runs upstream tests/models/transformers/test_backend.py::test_models as mandatory_pass on the same two models.

ProsRemoves duplicate work.

E · Unrealistic or niche configs

E1 · test_vllm_spyre_next::test_long_context_model_load

Shrink2.5 min → <1

Evidence: max_model_len=131072, eager, and it generates 32 tokens of "Hello World". It's really only a check that the config is honoured.

ProsKeeps the config check at almost no cost.
ConsIt no longer proves that a 128k engine can actually generate.
Recommended
  • Action: assert on llm.llm_engine.vllm_config.model_config.max_model_len and the KV-cache sizing without calling generate.
  • Mitigation: real long-context generation belongs in the attention tier and the quality gate, which test long KV directly.

E2 · test_compile::test_whole_model_granularity

Trunk-only6.0 min

Evidence: SPYRE_COMPILE_GRANULARITY=model is a non-default debug switch.

ProsNo default-path coverage lost.
ConsA torch-spyre change can break this switch unnoticed until trunk runs.
Recommended
  • Action: demote it.
  • Mitigation: also run it per PR when the diff touches the compile path (the paths: filter idea from axis 3).

E3/E4 · TP2 image parity and TP2 gemma-4 parity

Truncate (axis 1), full depth trunk-only47 + 27.2 min

Evidence: both compile a full model twice (TP1 and TP2), and together they're the two most expensive tests in the tier.

ProsTruncated parity keeps a TP-correctness check per PR at a fraction of the cost.
ConsBugs that appear only at full depth surface at trunk.
Recommended
  • Action: one decision for both pages: truncate per PR (axis 1 E2 and E6), and keep the full-depth params as trunk_only.
  • Mitigation: if truncating the mistral-format 14B doesn't work, make the image test trunk-only, and keep micro-g3.3 TP2 parity as the per-PR TP signal.

E5 · Token-major layout cases in tests/attention/test_spyre_attn.py

Shrink, measure firstattention tier

Evidence: token-major is the non-default layout (SPYRE_ATTN_KV_LAYOUT), required only for ALiBi and eager. About 10 cases still run it across the shape grid.

ProsThe attention tier gets cheaper.
ConsThe saving can't be measured from this dataset. Eager and ALiBi users still rely on token-major.
Recommended
  • Action: keep test_head_major_matches_token_major and the ALiBi and eager cases, and run the rest of the shape grid head-major only.
  • Mitigation: pull the attention tier's JUnit first to confirm it's worth doing. The parity test keeps token-major correct relative to head-major.

F · Oversized parametrize grids

F1 · models/test_gemma4_moe.py::test_persistent_matches_dense_reference

Shrink8.3 → ~2.8 min

Change: go from tokens {8, 16, 24, 32, 512, 512-tied} × tp {1, 2, 4} (18 cases) to {8, 24, 512-tied} × tp {1, 4} (6 cases). 24 stays because it doesn't divide the core count.

ProsThe edge cases stay: smallest, non-divisible, large and tied.
ConsTP2 MoE sharding is no longer tested here.
Recommended
  • Action: shrink it, but keep tp=2 instead of tp=4 if the per-PR distributed pool is 2-card. Match the TP sizes to the runners CI actually has.
  • Mitigation: run the full grid under nightly.

F2 · custom_ops/test_mlp.py

Shrink3.0 → ~1 min

Change: 4 functions × 24 shapes (96 cases). Reduce {tokens, heads, kv_heads, head_size, bias} pairwise to about 8 per function.

ProsPairwise coverage still catches most interaction bugs.
ConsA bug that needs three particular factor values together could slip through.
Recommended
  • Action: shrink it, and always include the shapes of models we serve (micro-g3.3, gemma-3, gemma-4) as explicit rows.
  • Mitigation: run the full grid under nightly.

The CPU-only grids (test_shape_bucketer 105, test_spyre_attn_bucketer 185, mrv2/test_layout 112 cases) take under a second in total. Leave them as they are.

Rollout

  1. Markers PR: register trunk_only and nightly and wire them into the Makefile, with trunk-failure alerting set up first.
  2. No-loss PR: A1, B, C4, E1, E2 and F. About 55 min per integration run.
  3. Paired PRs with axis 1: C1 with E3, D1, and the TP2 truncations (E2, E6). Each demotion lands together with its per-PR replacement.
  4. Probe hygiene: one hardware probe run for A2 and A3, plus the closed-issue checker.
  5. Ongoing: a quarterly ClickHouse query for slow tests that haven't failed in 30+ days.
