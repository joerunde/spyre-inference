Axis 2 · Audit for unnecessary or unrealistic tests

Plan · Nov 3, 2026 · What should exist at all, and in what form. Which tier each test runs in is decided by axis 3; making the remaining tests faster is axis 1. Every item was checked against main, CI data and, where it mattered, Spyre hardware.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

The audit covers all of tests/, measured against one cold integration run: 2,563 cases, 448 pytest-min. The ~2,100 cases under a second add up to about a minute, so it concentrates on the slow ones. This page keeps only what tiering can't do: deleting a test, shrinking it, re-linking it, or adding a cheap replacement.

A · Expected failures and stale markers

A1 · e2e/test_kernel_cache.py::test_kernel_cache[tp1-fresh]

Nightly6.9 min cold · 7.5 min warm (costliest case in a PR run)

Evidence: this is a strict xfail(raises=CacheGrewError) for a known cross-process cache-key bug: the fused RMSNorm+mm and attention keys differ between processes. No issue is linked. It still builds a cold and a warm engine on every run, and it's the single most expensive case in a warm PR run.

Change: add pytest.mark.nightly to the param, and link a new issue in the xfail reason.

ProsAbout 7 min off every tier, warm or cold.
ConsA fix is noticed only if somebody watches nightly. It's also the test that the compile-cache axis depends on.
Recommended
  • Action: move it to nightly and file the issue now.
  • Overcoming the cons: keep strict=True. Once the bug is fixed, nightly fails with XPASS, which forces the marker off. Assign the issue to the compile-cache owner, since fixing it unblocks cross-run cache hits.

A2 · Probes whose linked issue has closed

Validated on hardwareRe-link, don't deleteprobe tier

Evidence: in tests/probes/test_spyre_fallback_probes.py, the xfail on test_spyre_lm_head_unpadded_matmul_and_slice tracks #1918, which is closed. The probe tracking the open #3499 also cites #3502 and #3503, both closed. On hardware, both still fail (XFAIL). The bugs are real; only the issue links are stale.

Change: point each reason at a new open torch-spyre issue that describes the current failure.

ProsThe probe tier tracks live issues again, and each probe flags its fix with an XPASS.
ConsAs more issues close, links will go stale again.
Recommended
  • Action: re-link both, and keep the probes.
  • Overcoming the cons: add a small CPU-only check on ubuntu-latest. It reads issue numbers from xfail(reason=…) only, not from comments, treats a bare #N as torch-spyre, and flags any that are closed.

C · Checks other tests already cover

C2 · CPU test for granite-vision multi-tile preprocessing

Addseconds, CPU

Why: the multi-tile e2e test leaves the integration tier (axis 3), so multi-tile layout would only be checked in trunk.

Change: a CPU-only unit test in tests/multimodal/test_granite4_vision.py asserting tile count and placeholder token count for a 672 px image.

ProsCatches the most likely regression (tiling and token accounting) on every PR, at no device cost.
ConsDoesn't exercise the tower on card.
Recommended
  • Action: add it, in the same PR as the tier move.
  • Overcoming the cons: on-card multi-tile still runs in trunk, and the single-image granite-vision path through the same tower runs there too.

C3 · test_vllm_spyre_next::test_basic_model_load

Delete2.2 min

Evidence: asserts len(text) > 0 on eager micro-g3.3. test_compile[micro-g3.3] already covers that load with an exact-output check.

ProsNo coverage lost.
ConsThe file loses its simplest "does it load" smoke test, which is handy for debugging.
Recommended
  • Action: delete it.
  • Overcoming the cons: any load problem fails test_compile[micro-g3.3] first. Add the one-line node ID for that test to docs/contributing/README.md as the quick smoke test.

D · Duplicates of upstream vLLM tests

D1 · e2e/test_transformers_backend.py::test_transformers_matches_native

Drop the micro-g3.3 case~7 of 14.3 min

Evidence: upstream_tests.yaml runs upstream tests/models/transformers/test_backend.py::test_models as mandatory_pass on the same two models. The Llama-3.2-1B case (head_dim 64) takes our padded-head path; micro-g3.3 (head_dim 128) doesn't.

ProsRemoves duplicate work.
ConsUpstream tests run only in regression and trunk, so dispatched runs lose the micro-g3.3 generation check.
Recommended
  • Action: drop only the micro-g3.3 case. Keep Llama-3.2-1B, which tests the Spyre-specific padding.
  • Overcoming the cons: test_transformers_backend_compile (3.3 min) still covers the backend on every PR, and micro-g3.3 still generates there through test_compile.

E · Unrealistic configs

E1 · CPU config check for 128k context

Addseconds, CPU

Why: test_long_context_model_load builds an engine at max_model_len=131072 only to show the config is honoured, and it leaves the integration tier (axis 3).

Change: a CPU-only test that builds EngineArgs(max_model_len=131072, …).create_engine_config() and asserts model_config.max_model_len, with no device and no engine.

ProsA long-context config regression is caught on every PR in seconds.
ConsDoesn't prove that a 128k engine actually generates.
Recommended
  • Action: add it, and leave the engine test unchanged in trunk.
  • Overcoming the cons: the trunk engine test keeps that proof, and the attention tier tests long KV directly.

F · Oversized parametrize grids

F1 · custom_ops/test_mlp.py

Shrink3.0 → ~1 min

Change: today it's 4 functions × 24 shapes (96 cases). Reduce the {tokens, heads, kv_heads, head_size, bias} grid pairwise, to about 8 cases per function.

ProsPairwise coverage still catches most interaction bugs.
ConsA bug that only appears with three particular factor values together could slip through.
Recommended
  • Action: shrink it, and always keep the shapes of the models we serve (micro-g3.3, gemma-3, gemma-4) as explicit rows.
  • Overcoming the cons: run the full grid nightly.

Rollout

  1. No-loss PR: C3 (delete), D1 (drop the micro-g3.3 case), F1 (shrink), and the C2 and E1 CPU tests. About 10 min off every tier.
  2. With axis 3's marker PR: the items in Handled by axis 3 move tiers there; C1 and E3 land together with axis 1 E3 (nano gemma-4), so each demotion comes with its per-PR replacement.
  3. Infrastructure: a nightly marker with its cron workflow, and the Slack trunk-failure alert; then A1.
  4. Probe hygiene: A2 re-links, and the closed-issue checker.
  5. Ongoing: review with axis 3 quarterly; query ClickHouse for slow tests that haven't failed in 30+ days.

How this was validated
  • Code: every item was checked against main 593b5709, and every linked issue's state against GitHub.
  • CI data: JUnit timings from regression run 41691109984, integration run 41512695264 and the original dataset run 41363344874.
  • Hardware: the probes (A2), the nano replacement for C1 and E3, and the truncation attempts all ran on the team's 4-card Spyre host. Its torch-spyre is older than main's pin (64870622 vs f8a09bb).
