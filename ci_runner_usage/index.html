1. Summary

~34.6kSpyre runner-hours across the three repos in 14 days (job running time, no queue time)
46%of that is spyre-inference, the largest share
64%of spyre-inference's hours come from spyre-ci (spyre-test) dispatches
~70%of those dispatched hours are for torch-spyre PRs, not ours
  • spyre-inference's biggest consumer is integration-tests.yaml, dispatched by spyre-ci[bot]: ~10.3k runner-hours from ~750 runs. Most of those test a torch-spyre PR against our main.
  • One integration-tier run costs ~8.7 runner-hours (15 jobs). About 87% of the pytest time is ~60 end-to-end model tests. The other ~2,500 tests take under an hour in total.
  • Failures in this tier are almost always global: when a torch-spyre change breaks us, nearly every shard fails together. Cheap tests would catch those breaks as well as the 40-minute model runs do.
  • Proposed: trim the integration tier to its cheap core (~2.5 runner-hours per run, saving roughly 5k runner-hours per two weeks, ~15% of all three repos' usage). Also stop skipped matrix jobs from taking a Spyre card, make the multimodal tests cheaper (45% of the tier's pytest time), audit and slim down the regression set, and get the compile cache working on dispatched runs. Everything proposed is in this repo. Details in §7.

6. Scheduling waste on top of the tests

  • Skipped matrix jobs still take a Spyre card. The quality-gate, attention, probe, TP4 and upstream entries (~30 per run) fall outside the tier. Each still gets an x86_64,spyre_pf_x1 runner, only to run the "skip" step (0–3 min each). The runner-hours are small, but that's ~30 extra allocations per dispatch while the pool is already queued. This also applies to our own PR runs that aren't in those tiers.
  • ~29% of dispatched integration runs end cancelled (172 of 597). The concurrency group in .github/workflows/integration-tests.yaml (line ~119) keys on pr_url_hash with cancel-in-progress, so a new torch-spyre push kills the run in flight. That's the right outcome, but it happens after the runners have been allocated and partly used.
  • Failures are global. In 40 sampled failed integration runs, nearly every smoke and distributed shard failed together. A breaking torch-spyre change tends to take down everything, so a short first stage would catch it.

7. Proposed changes

Ordered by expected savings per unit of effort. Hour estimates are per 14 days, against the ~34.6k total.

R1 · Trim the integration tier to a cheap core

Owner: spyre-inferenceSaves ≈ 5k h / 14 dNeeds agreement on coverage

Mark the heavy e2e cases with a new marker (e.g. integration_heavy, registered in pyproject.toml). Exclude it from the smoke and distributed targets only when TEST_TYPE=integration, so regression and trunk keep running everything. Proposed drop list (~339 of 448 pytest-minutes):

  • All of test_multimodal.py (Ministral-3-14B and gemma-4-26B vision): 113 min
  • In test_distributed_tp2.py: the compiled image prompt, gemma-4-26B text and fp8 cases (79 min). Keep the micro-g3.3 parity cases.
  • In test_compile.py: gemma-4-26B, gemma-4-31B and test_whole_model_granularity (29 min). Keep micro-g3.3, micro-g3.3-fp8, gemma-3-1b, the transformers-backend compile and the warmup-coverage check.
  • test_transformers_backend, test_kv_cache_determinism, test_fp8_kv_cache, test_vllm_spyre_next, the gemma-4 / pixtral model-level pipeline checks, and the heavy CLIP cases
  • The test_kernel_cache variants other than tp1-shared (tp1-fresh is a known xfail, see R4), the eager test_prefix_caching, eager granite-vision, and all encoder rerankers except bge-reranker-v2-m3

What's left (~93 min on 1-card runners, ~16 min on 2-card) fits in ~4 smoke shards + 1 distributed shard + attention smoke ≈ 2.5 runner-hours per run, down from 8.7. Rebalance with the repo's rebalance-test-shards skill, which keeps the Makefile *_SHARDS counts and the _test_matrix.yaml entries in step; tests/test_sharding.py guards that. The _test_matrix.yaml comment saying the tier "MUST keep" the smoke and torch.compile e2e coverage still holds: compiled micro-g3.3, gemma-3 and fp8 stay in.

Savings estimate: ~71% of the 10.3k spyre-test hours are integration-tier runs (~7.3k h; the other ~28% are regression runs, see R4). Cutting each run by ~71% saves ~5.2k h. Our own PR and merge-queue runs are unaffected.

R2 · Don't allocate runners for matrix entries outside the tier

Owner: spyre-inferenceSaves ≈ 30 card allocations per run, ~0.5 h/runSmall change

Add a GitHub-hosted job ahead of test in _test_matrix.yaml that filters the include list by inputs.test_type and outputs JSON. test then uses matrix: ${{ fromJSON(needs.plan.outputs.matrix) }}, so out-of-tier entries never request a spyre_pf_x1 runner. This applies to every caller (integration, unit, PR regression), so it also helps queueing for our own PRs. Watch for anything that keys on the full job list, such as the "Test matrix result" aggregator, the pod-level retry collector and tests/test_sharding.py.

R3 · Make the multimodal tests cheaper

Owner: spyre-inference≈ 200 of 448 pytest-min in an integration runHelps every tier

Multimodal and vision tests are 45% of the integration tier's pytest time, and almost all of it is five tests that build a full product model:

TestModelMin
test_distributed_tp2::test_tp2_compiled_image_prompt_matches_tp1Ministral-3-14B, TP1 + TP247.0
test_multimodal::test_gemma4_single_image_prompt_produces_output[compiled]gemma-4-26B-A4B41.5
test_multimodal::test_single_image_prompt_produces_output[compiled]Ministral-3-14B26.5
test_multimodal::test_warmup_covers_text_only_token_embedding_on_multimodal_modelMinistral-3-14B24.9
test_multimodal::test_gemma4_single_image_prompt_produces_output[eager]gemma-4-26B-A4B10.7
granite-vision (3), two-image, Pixtral eager, gemma-4 / Pixtral model-level, CLIPvarious~51

Most of these only assert that generation is non-empty, so the expensive part is building and compiling the model, not checking it. Options, roughly cheapest first:

  • Build each compiled model once. The compiled single-image and text-only-warmup tests both build and compile the same Ministral-3-14B engine (~51 min together). One test with SPYRE_COMPILE_GUARD=error can send both a text-only and an image prompt to a single engine. That covers both cases at roughly half the cost.
  • Smaller models via layer truncation. The file says there's "no smaller stand-in" for the 14B. But hf_overrides can truncate the decoder (text_config.num_hidden_layers, and the vision tower's layer count) while keeping the architecture and all the code paths: the Pixtral tower, projector, gemma-4 MoE and offset-group pool. test_transformers_backend.py and tests/models/test_gemma4_mm.py already build 1–4-layer configs. Compile time scales with distinct graphs, not layers, so check this with SPYRE_COMPILE_GRANULARITY; load time and the per-layer work still shrink.
  • Dummy weights. For "produces output" checks, load_format="dummy" skips reading 14–26B of weights from the shared HF cache. Pair it with ignore_eos so random weights can't end generation early. Keep real weights wherever output is compared, such as the TP1/TP2 parity test.
  • Tighter warmup buckets. These tests use max_model_len=512 and compile_sizes=[1, 512], but the prompts are at most two 176×176 images (Pixtral) or one ≤280-token image (Gemma 4). Warmup compiles every KV × query bucket and every vision budget up to those limits. Count the graphs warmup records for each test, then pin max_num_batched_tokens, max_model_len and the vision budget to the smallest values that still cover the prompt. Use the SPYRE_ATTN_KV_BUCKETS / SPYRE_ATTN_QUERY_BUCKETS overrides where the defaults are larger than needed.
  • One compiled TP2 multimodal case is enough. The 47-minute TP1-vs-TP2 image parity test compiles the 14B twice. A truncated model, or running it only in trunk, would remove most of that.

Once these are cheap, some can move back into the integration tier that R1 drops them from, since vision lowering is exactly what a torch-spyre change can break.

R4 · Audit for unnecessary tests, then strip down the regression set

Owner: spyre-inferenceTouches ≈ 8.5k h / 14 dNeeds agreement on coverage

Audit first. Go through the ~450 cases that take more than a second; the other 2,110 integration cases total about 1 minute and aren't worth the effort. Remove or demote tests that:

  • Are expected to fail. tests/e2e/test_kernel_cache.py::test_kernel_cache[tp1-fresh] is an xfail for a known cache-key bug (fused RMSNorm+mm and attention keys differ between processes) and costs ~7 min per run. It tells us nothing until the bug is fixed; move it to a manual or nightly marker.
  • Duplicate another test at the same cost. For example, two tests that build the same compiled model (see R3), or an eager twin of a compiled test that adds no assertions.
  • Only assert "produced output" for a model the quality gate already checks for correctness.
  • Haven't failed in weeks. Every run's JUnit is already ingested into ClickHouse by push-to-clickhouse.yaml, so per-test failure history is a query away. A slow test that never fails is a candidate for trunk only.

Then strip down regression. It means "every config", and it runs in two places: the direct test_each_commit.yaml on our PRs and merge queue (~5.6k h), and ~28% of the spyre-test dispatches (~2.9k h, mostly for our own PRs). One run costs ~14 runner-hours across ~45 jobs. Breakdown from 2 recent successful runs:

Ideas to evaluate, in order:

  • Keep only one of eager and compiled where both run (test_multimodal, test_prefix_caching, test_granite_vision, test_clip_embeddings). Compiled is the default serving path; eager can move to trunk.
  • Move what the audit flags to trunk only, so it runs on push to main rather than on every PR push.
  • Use the merge queue as the full gate and run a reduced regression on PR pushes. The full set then runs once per merge rather than once per push.

The same integration_heavy-style marker mechanism from R1 works here. Since trunk is "same coverage as regression" today, splitting them is mostly test_types edits in _test_matrix.yaml.

R5 · Make the compile cache work on dispatched runs

Owner: spyre-inferenceApplies to ≈ 10k h / 14 d of dispatched runsInvestigate first

Most of the integration tier's time is compiling models. Our CI already shares inductor and Spyre kernel caches between jobs over NFS (.github/scripts/nfs_compile_cache.py, used by .github/actions/run-matrix-config/action.yml). The dispatched runs can't use it:

  • The Restore compile cache (NFS) step is skipped whenever use_prebaked_image, torch_spyre_ref or rpm_names is set. Dispatched runs for torch-spyre PRs use a per-PR prebaked image (runs-on label image_id_<hash>_r<n>), so they always compile cold. Confirmed in a recent dispatched run's log: use_prebaked_image: true, and both Restore compile cache (NFS) and Save compile cache delta (NFS) report skipped.
  • The cache key is the hash of uv.lock + spyre-rpms.lock. Those files don't describe the stack inside a prebaked image, so the key would be wrong even if the gate were lifted.
  • Underneath that, a torch-spyre change can really change generated kernels, and inductor's own cache key includes the torch-spyre version. A naive shared cache would miss anyway, or worse, serve stale kernels.

Things to investigate:

  • Key the cache on the image's actual stack. Derive the key from the installed torch-spyre version or commit plus RPM versions, for example from the artifact-identity job's output, rather than our lockfiles. Then repeated pushes to the same torch-spyre PR, and every shard in a run, share one cache. Same-key reuse within a PR is likely where most of the win is.
  • Measure the hit rate across torch-spyre versions. Inductor's FX-graph cache keys on the torch-spyre version, but the Spyre kernel cache (SPYRE_KERNEL_CACHE) may key on generated code. If kernels are stable across most torch-spyre commits, a cache keyed on kernel source would still hit after a bump. tests/e2e/test_kernel_cache.py and test_kernel_cache_sharing.yaml already exercise this path. Its tp1-fresh xfail (see R4) documents a known gap: some kernel cache keys differ whenever the model is lowered again in a new process. Fixing that is probably a prerequisite for cross-run hits.
  • Keep it safe: restore read-only for dispatched runs, so a torch-spyre PR's kernels never write into the cache our own PRs read.

R6 · Fast-fail first stage (optional, after R1)

Owner: spyre-inferenceSaves most of a broken PR's run

Run the non-e2e tests (~57 min, one shard) first and start the e2e shards only if they pass, via needs:. Because failures are global, a broken torch-spyre PR would cost ~1 runner-hour instead of a full run. The cost: a passing run's wall-clock grows by the first stage's length.

8. Method, caveats and how to reproduce

  • Run listing: every workflow run created Oct 19 – Nov 1 via GET /repos/torch-spyre/{repo}/actions/runs?created=…, split into day, 3-hour or 1-hour windows to stay under the API's 1,000-result cap. That gave 1,883 runs for hf-adapters, 8,370 for spyre-inference and 44,127 for torch-spyre.
  • Runner-hours: from /actions/runs/{id}/jobs, summing completed_at − started_at over jobs not on ubuntu-latest / the "GitHub Actions" runner group. Run-level wall-clock includes queueing and was not used.
    • census: spyre-inference integration-tests (spyre-test) was measured on 610 of 750 runs and test_each_commit on 438 of 509, then scaled to all runs. A full count of the other heavy workflows was stopped to stay inside the 5,000/h API budget.
    • sample40 / sample12: the mean of 40 or 12 random completed runs, scaled by the run count.
  • Trigger category: spyre-test if actor or triggering_actor is spyre-ci[bot]; relay if it's pytorch-fdn-cross-repo-ci-relay[bot]; direct otherwise. spyre-ci also dispatches runs for upstream commits, not only /spyre-test comments, and the run metadata can't tell those apart.
  • Waiting hours: started_at − created_at per Spyre job. That includes time a job waited on its needs:, so treat it as a relative signal.
  • Test inventory: one run's JUnit artifacts (junit-test-*), so per-test minutes are approximate. Shard durations across 4 runs agree within ~15%.
Reproduce the main numbers 
# 1. list runs for one day (repeat per day; split into hours when a window returns 1,000)
gh api "repos/torch-spyre/spyre-inference/actions/runs?created=2026-10-27&per_page=100" --paginate \
  -q '.workflow_runs[] | [.id,.name,.event,.actor.login,.triggering_actor.login,.status,.conclusion,.created_at,.run_started_at,.updated_at,.display_title,.head_branch,.run_attempt,.path] | @tsv'

# 2. Spyre runner time for one run
gh api --paginate "repos/torch-spyre/spyre-inference/actions/runs/<id>/jobs?per_page=100&filter=all" \
  -q '.jobs[] | select(.started_at and .completed_at) | [.name, (.labels|join(",")), .runner_group_name,
       ((.completed_at|fromdate)-(.started_at|fromdate))] | @tsv'

# 3. who a dispatched run was for: read pr_url_hash from its "Log upstream dependant tool regression trigger" job
gh api --allow-escape-sequences repos/torch-spyre/spyre-inference/actions/jobs/<job_id>/logs | grep 'PR URL hash'
#    then compare with: printf %s https://github.com/torch-spyre/torch-spyre/pull/<n> | sha256sum

# 4. per-test timings for a run
gh run download <id> -R torch-spyre/spyre-inference -p 'junit-*' -D ./junit
