Axis 1 · Reduce test execution time

Plan · Nov 3, 2026 · Keep the same tests and coverage, spend less time per run. Removing or demoting tests is axis 2; the two pages share the decisions below.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Why it's slow

  • Every e2e test builds its own engine. No test shares an LLM through a module- or session-scoped fixture, and many build two (TP1 and TP2, fp16 and fp8, APC and plain, transformers and native). Most of the time goes into build and compile, not into the checks.
  • The same model is built over and over. Four test_compile tests and three test_kernel_cache cases each build the same compiled micro-g3.3 config, and the two compiled Ministral-14B tests share one config.
  • Full-size models are used where a small one would do. Most multimodal tests only check text.strip(), yet they load 14–26B of weights.
  • Two legs run one test each and set the wall clock. smoke-0 runs only the gemma-4 image test (41.5 min) and distributed-0 only the TP2 image test (47 min). The other legs take about 28–31 min.

Phase 1 · Consolidate and truncate (no coverage change)

E1 · One Ministral-14B compiled engine for the text-only and image checks

~25 minEffort Stests/e2e/test_multimodal.py

Change: merge test_single_image_prompt_produces_output[compiled] (26.5 min) and test_warmup_covers_text_only_token_embedding_on_multimodal_model (24.9 min), which call _generate with the same config. Let _generate take a list of prompt batches and run them on one LLM, text-only first, then the image prompt.

ProsBoth checks stay, and one full 14B build and compile goes away.
ConsThe image test doesn't arm SPYRE_COMPILE_GUARD=error today. If the Pixtral tower compiles on first use, the merged test fails. A failure in step one also hides the result of step two.
Recommended
  • Action: do this first; it's the best saving per hour of work.
  • Mitigation: run the text-only step under SPYRE_COMPILE_GUARD=error and the image step under warn, asserting no guard warning for the decoder. Use a pytest-subtests-style subtest (or two separate assertion messages) so each check reports separately.

E2 · Truncate gemma-4 in the TP2 parity test

27.2 → a few minEffort S/Mtests/e2e/test_distributed_tp2.py

Change: in the gemma-4-26B-A4B-text param of test_tp2_compiled_llm_generate_matches_tp1, pass hf_overrides={**GEMMA4_TEXT_BACKBONE_OVERRIDE, "text_config": {"num_hidden_layers": 4}}.

ProsTP1 vs TP2 still compares like with like: both sides are truncated the same way and use real weights. MoE and all-reduce stay covered.
ConsMerging the override may need nested-dict handling. Bugs that appear only at full depth (later layers, long KV) are no longer caught per PR.
Recommended
  • Action: do it, and keep the full-depth param as trunk_only.
  • Mitigation: choose the layer count from gemma-4's sliding/full pattern so at least one layer of each type stays, and assert the layer types in the test so a config change can't silently drop one. Add a small helper that deep-merges hf_overrides; E3, E5 and E6 reuse it.

E3 · Truncate the remaining gemma-4 compile row

~8–10 minEffort Stests/e2e/test_compile.py

Change: the audit moves gemma-4-31B-text to trunk (C1). Truncate the remaining gemma-4-26B-A4B-text row of test_basic_llm_inference with the E2 helper and regenerate its reference string.

Prostorch-spyre PRs keep a gemma-4 MoE compile signal at a fraction of the cost.
ConsA truncated model's exact output is arbitrary text, so the reference string has to be regenerated and can't be checked by eye.
Recommended
  • Action: do it, in the same PR as audit C1, so gemma-4 coverage never drops out of the integration tier.
  • Mitigation: generate the reference on CPU, or on the full model at trunk, and record in the test how it was produced. Compare token IDs rather than strings.

E4 · Fold the compile-guard test into test_basic_llm_inference

~3 minEffort Stests/e2e/test_compile.py

Change: test_warmup_covers_every_compile_a_request_needs uses the same model and shapes as the [micro-g3.3] row and differs only in the guard. Delete it and set SPYRE_COMPILE_GUARD=error in _assert_compiled_output.

ProsThe warmup guard then covers fp8, gemma-3 and gemma-4 too, so coverage grows.
ConsA gemma row may fail on a real warmup gap and block the PR until that's fixed.
Recommended
  • Action: do it in two steps.
  • Mitigation: first set the guard to error for micro-g3.3 and to warn for the others, logging what fires. Once the warnings are fixed, or tracked as an xfail with an issue link, switch every row to error.

Phase 2 · Smaller models and tighter shapes (measure first)

E5 · gemma-4 vision (compiled): truncated layers and dummy weights

~25–30 of 41.5 minEffort Mtests/e2e/test_multimodal.py

Change: in test_gemma4_single_image_prompt_produces_output[compiled], add load_format="dummy", SamplingParams(ignore_eos=True), and hf_overrides that lower num_hidden_layers for both the text model and the vision tower. The [eager] twin goes to trunk (audit B).

ProsThe run no longer reads 26B of weights from the shared HF cache, and warmup has fewer graphs to build. The tower, projector and MoE code paths are unchanged.
ConsCompile time scales with the number of distinct graphs, not with layer count, so the saving may be smaller than expected. Dummy weights can produce NaN and don't exercise real numerics.
Recommended
  • Action: do it, after counting graphs on hardware once (warmup logs list the recorded variants).
  • Mitigation: if truncation saves little, keep only the dummy weights, which avoid the 26B weight read. Assert that the output is non-empty and contains no NaN logprobs. Real-weight numerics stay covered by the full model in the quality gate and at trunk.

E6 · Truncate the TP2 image parity test

~35–40 of 47 min (longest leg)Effort Mtests/e2e/test_distributed_tp2.py

Change: test_tp2_compiled_image_prompt_matches_tp1 builds the 14B twice. Cut the decoder and vision layers with hf_overrides. The test uses config_format="mistral", so the overrides must reach params.json.

ProsRemoves the longest leg in the tier, and the distributed pool frees up first.
ConsNobody has tested overrides on a mistral-format config yet. Bugs that show up only at full depth move to trunk.
Recommended
  • Action: start with a half-day spike to prove the override works on mistral format, and keep the full-depth run as trunk_only.
  • Mitigation: if the override doesn't work, switch the integration case to the HF-format checkpoint of the same model, where hf_overrides is known to work. Only if that also fails, fall back to audit E3 (trunk-only), and keep the micro-g3.3 TP2 parity case as the per-PR TP signal.

E7 · Tighten warmup sizes to what each test's prompts need

~2–5 min per testEffort S each
  • test_multimodal.py: lower MAX_MODEL_LEN from 512 to 256 for the Pixtral rows. test_distributed_tp2.py already serves the same 176×176 image at 256.
  • test_granite_vision.py: sets max_model_len=4096 with no compile_sizes, so warmup covers every bucket up to 4096. Size each test to its own prompt. The multi-tile test goes to trunk (audit C3), so the per-PR single-image test can be much smaller.
  • test_prefix_caching.py[compiled]: max_model_len=512 with four engines. Set it to the shared prefix plus the question plus 16.
ProsWarmup records fewer KV × query buckets. Each change is one line.
ConsThe tests stop covering the larger buckets that production serves. A size that's too tight fails noisily.
Recommended
  • Action: do it, one file per PR, with before/after warmup variant counts in the PR description.
  • Mitigation: derive each size from the prompt's token count (tokenize in the test, add a margin) rather than hard-coding it, so a prompt change can't break it. Large-bucket coverage stays in the attention tier and the quality gate, which run at serving lengths.

E8 · Share one engine across the same-shape KV-determinism tests

~4 minEffort Stests/e2e/test_kv_cache_determinism.py

Change: test_logprobs_do_not_depend_on_earlier_requests and ..._in_a_batch both use max_model_len=256 and a 128-token prefill. Give them one module-scoped engine fixture with compile_sizes=[128, _BATCH_NUM_SEQS, 1].

ProsSets up a pattern that other files can reuse.
ConsModule-scoped engines are new in this repo. The fixture must release the card reliably, and state can leak between tests. For a determinism test, that leak is exactly the thing under test.
Recommended
  • Action: use this file as the pilot for a shared-engine fixture in tests/conftest.py, then extend it to the micro-g3.3 builds in test_compile.
  • Mitigation: tear down with llm.llm_engine.engine_core.shutdown() plus a device-free check in the finalizer. Call reset_prefix_cache() between tests, and order the tests so the "earlier requests" one runs on a fresh cache.

Phase 3 · CI plumbing

E9 · Fast-fail first stage (R6)

Saves most of a broken runEffort S/M.github/workflows/_test_matrix.yaml

Change: run a first-stage shard, and make the e2e shards depend on it with needs:.

ProsWhen a torch-spyre PR breaks things, every shard fails together. With this stage it costs about 1 runner-hour instead of about 8.7.
ConsA passing run takes longer by the length of the first stage, about 57 min if it runs every non-e2e test.
Recommended
  • Action: do it, but with a slim first stage rather than all non-e2e tests.
  • Mitigation: make the first stage the custom-op tests plus compiled micro-g3.3 test_basic_llm_inference, about 10–15 min, which is enough to catch a global break. Use it only for dispatched torch-spyre runs, where most runs come from other repos' PRs, and leave our own PR runs fully parallel.

E10 · Rebalance shards once E1–E6 land

Wall clock and cards heldEffort SMakefile, _test_matrix.yaml

Change: run the rebalance-test-shards skill. Once the two single-test legs are gone, SMOKE_SHARDS=11 and DIST_SHARDS=3 can shrink.

ProsFewer Spyre cards allocated per run, and a shorter tail.
Constests/test_sharding.py has to stay in lockstep with the matrix. Rebalancing too early locks in stale durations.
Recommended
  • Action: do it last, once, from the durations of 3–4 runs after Phase 2 lands.
  • Mitigation: the skill already keeps the Makefile, the matrix and test_sharding.py in lockstep. Re-run it whenever a leg drifts more than about 20% from the median.
