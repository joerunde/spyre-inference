Axis 1 · Reduce test execution time

Plan · Nov 3, 2026 · Same tests and coverage, less time per run. Every action below was validated on Spyre hardware. Removing or demoting tests is axis 2.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Why it's slow

  • Every e2e test builds its own engine, and many build two (TP1 and TP2, fp16 and fp8, APC and plain). Most of the time goes into compiling, not into the checks.
  • Full-size models are used where a small one would do. The gemma-4 decoder tests load 26–31B weights just to check a short generation.
  • Some tests warm up shapes their assertions never use. The gemma-4 budgets test compiles six vision budgets but needs three, and on a cold cache it times out at 3600 s.
  • Cold runs are the problem. Dispatched torch-spyre runs skip the compile cache. The same tests are 4–10× cheaper on our own warm PR runs, so the savings below land mostly on dispatched runs and runs after a lockfile bump (details).

Plan

In priority order. "Cold min" is per integration run, from JUnit data. "Validated" means a hardware run of main 593b5709 on the team's Spyre host. That host's torch-spyre is older than main's pin, so re-check each change in its own PR's CI.

E1 · gemma-4 budgets test: only the 3 budgets it needs

ValidatedFixes a cold-cache timeoutEffort Stests/e2e/test_multimodal.py

Problem: test_gemma4_request_max_soft_tokens_replays_warmed_budgets (#1376, timeout(3600)) warms six vision budgets (64, 128, 256, 280, 576, 1152) on gemma-4-26B-A4B. On a cold compile cache, warmup alone runs past the limit, so no request is ever sent. It timed out in job 126072048399 (PR #1467, a vLLM bump). Every lockfile bump and most dispatched runs start cold. Warm, the test passes in about 7 min.

Change: encoder_budgets=(280, 576, 1152). Each remaining budget serves an assertion:

  • 280 (rounded up to 320) carries the default image and the packed pair.
  • 576 serves max_soft_tokens=560.
  • 1152 serves 1120, the image that runs alone.

The encoder graph manager warms exactly this list, so the change is one line.

Hardware result: on a cold cache, the three-budget version passed in 22.6 min and the unchanged six-budget test in 29.4 min, with all assertions holding. Vision warmup drops from 15 min to 7. The host ran faster than CI, where the six-budget test hit the timeout, so read the result as relative: about 25% off the test and vision warmup halved.

ProsA one-line change that keeps testing exactly what #1376 added: budget selection, packing, and graph hits and misses.
ConsBudgets 64, 128 and 256 are no longer warmed in this test. A cold run still takes 20-plus minutes, so a slow CI host could approach the limit again.
Recommended
  • Action: land this first. Right now the test fails every vLLM and torch-spyre bump PR.
  • Overcoming the cons:
    • Small budgets: no assertion uses them, and the default-budget path still exercises small images. If they matter, cover budget selection in a CPU-only unit test, which needs no compile.
    • Headroom: state the cold time in the PR, and let the compile-cache work (axis 4) take the rest. If a cold CI run still exceeds 30 min, also lower max_model_len from 2048 to about 1,300 (1152 image tokens plus the prompt).

E2 · Merge the two Ministral-14B compiled tests onto one engine

Validated~35 minEffort Stests/e2e/test_multimodal.py

Change: merge test_single_image_prompt_produces_output[compiled] (26.5 min) and test_warmup_covers_text_only_token_embedding_on_multimodal_model (24.9 min), which build the same engine. The merged test sends the text-only prompt first, then the image prompt, under SPYRE_COMPILE_GUARD=error.

Hardware result: passes in 14.5 min, against 51 CI-min for the two tests. The guard didn't fire, so the vision tower is fully warmed.

ProsBoth checks stay, one 14B build and compile goes away, and the image path now also runs under the compile guard.
ConsIf the text-only step fails, the image step doesn't run.
Recommended
  • Action: do it.
  • Overcoming the cons: give each step its own assertion message, so a failure names the step that broke. The guard is read once per engine, but error passes for both steps, so that doesn't matter.

E3 · gemma-4 decoder tests on a nano gemma-4

Validated~23 minEffort Stests/e2e/test_compile.py, tests/e2e/test_distributed_tp2.py

Change: point the gemma-4-26B-A4B-text rows of test_compile::test_basic_llm_inference and test_distributed_tp2::test_tp2_compiled_llm_generate_matches_tp1 at joerunde/gemma-4-moe-nano, keeping GEMMA4_TEXT_BACKBONE_OVERRIDE. Nano has 6 text layers, MoE with 128 experts, both sliding-window and full attention, and real weights. Regenerate the test_compile reference output from it.

Hardware result: test_compile passes in 4.2 min (13.2 in CI). TP1-vs-TP2 token IDs match in 12.5 min (27.2 in CI).

ProsSame architecture and code paths (MoE routing, both attention kinds, TP all-reduce) with real weights, so the parity check stays meaningful.
ConsThe full 26B decoder isn't compiled on every PR. Nano sits in a personal HF namespace and isn't in the CI model cache list.
Recommended
  • Action: do it, in the same PR that moves the full-size rows out of the integration tier (audit C1).
  • Overcoming the cons:
    • Full-size coverage: the quality gate still compiles 26B-A4B and 31B on every regression run, and trunk keeps the full-size rows.
    • Provenance: with the author's OK, mirror nano to an org HF repo, pin its revision, and add it to .github/cache_config/hf_models_and_datasets.yaml.

E4 · Compile guard on every test_compile row, delete its twin

Validated~3 minEffort Stests/e2e/test_compile.py

Change: test_warmup_covers_every_compile_a_request_needs builds the same micro-g3.3 engine as test_basic_llm_inference[micro-g3.3] and differs only in the guard. Delete it and set SPYRE_COMPILE_GUARD=error in _assert_compiled_output for every row.

Hardware result: micro-g3.3, micro-g3.3-fp8 and gemma-3-1b all pass under error.

ProsThe warmup guard now also covers fp8 and gemma-3: more coverage, one fewer engine build.
ConsA future row that misses a warmup shape will fail the PR instead of just running slower.
Recommended
  • Action: do it.
  • Overcoming the cons: failing the PR is the point. It catches a warmup gap before it reaches serving, and the guard message names the missing shape.

E5 · Merge the two KV-determinism tests onto one engine

Validated~4 minEffort Stests/e2e/test_kv_cache_determinism.py

Change: merge test_logprobs_do_not_depend_on_earlier_requests and ..._in_a_batch, which share a shape, into one test that builds one engine with compile_sizes=[128, _BATCH_NUM_SEQS, 1]. It runs the earlier-requests check first, calls llm.reset_prefix_cache(), then runs the batch check. It has to be one test, not a shared fixture: the test plugin kills whatever holds the card after every uses_subprocess test.

Hardware result: the merged test passes, and so do the two originals.

ProsOne fewer engine build, with no change to the test plugin.
ConsThe batch check runs on an engine the first check already used, and engine state is exactly what a determinism test cares about.
Recommended
  • Action: do it.
  • Overcoming the cons: run the earlier-requests check on the fresh engine, and reset the prefix cache before the batch check. The batch check compares requests within one batch, so prior use of the engine doesn't weaken it.

E6 · Fast-fail first stage for dispatched runs (R6)

Saves most of a broken runEffort S/M.github/workflows/_test_matrix.yaml

Change: when test_type == 'integration', which is what dispatched torch-spyre runs send, run one shard first. It holds the custom-op tests (about 12.5 min) plus compiled micro-g3.3 test_basic_llm_inference, and the e2e shards wait on it with needs:. Our own PR runs (regression, trunk) stay fully parallel.

ProsA breaking torch-spyre change fails nearly every shard together, so with this stage a broken dispatched run costs about 1 runner-hour instead of 8.7.
ConsA passing dispatched run takes about 15 min longer.
Recommended
  • Action: do it, for dispatched runs only.
  • Overcoming the cons: keep the first stage at about 15 min. torch-spyre authors care about the verdict more than the wall clock, and our own PRs are unaffected.

E7 · Rebalance shards once E1–E5 land

Wall clock and cards heldEffort SMakefile, _test_matrix.yaml

Change: run the rebalance-test-shards skill on the durations of 3–4 runs after E1–E5 land. With the long single-test legs gone, SMOKE_SHARDS=11 and DIST_SHARDS=3 can shrink.

ProsFewer Spyre cards per run, and a shorter tail.
ConsRebalancing too early locks in stale durations.
Recommended
  • Action: do it last, once.
  • Overcoming the cons: the skill keeps the Makefile, the matrix and tests/test_sharding.py in step. Re-run it when a leg drifts more than about 20% from the median.

Cold vs warm runs

The minutes above come from dispatched integration runs. They use a prebaked image and skip the NFS compile cache (R5), so every test compiles cold. On our own PR regression runs, the same tests are 4–10× cheaper: smoke plus distributed take about 126 pytest-min there, against about 400 in a dispatched run.

  • This plan mainly helps dispatched torch-spyre runs, and our own runs after a uv.lock or spyre-rpms.lock bump.
  • Cold runs hit the 3600 s timeout first in the multimodal tests, so E1 and E2 are reliability fixes as well as cost cuts.
  • The compile-cache axis removes the same cold cost directly, and is worth more than any single item here.

Considered and dropped

Kept here so nobody re-tries these without new information.

It works only with load_format="dummy", which loses the reference-output and parity checks. Nano (E3) replaces it for the decoder.

How this was validated
  • Code: each action was checked against main 593b5709: the tests, vLLM's config loading and the CI test plugin.
  • Hardware: each validated action ran as a modified test on the team's 4-card Spyre host, one run at a time, with an empty compile cache wherever cold time mattered. The host has an older torch-spyre than main pins (64870622 vs f8a09bb), so failures that could come from the installed stack, such as the nano vision tower, need a recheck on CI.
  • CI data: JUnit timings from regression run 41691109984 and integration run 41512695264, and the logs of job 126072048399.
