Axis 1 · Reduce test execution time

Plan · Nov 3, 2026 · Keep the same tests and coverage, spend less time per run. Removing tests is axis 2.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Why it's slow

  • Every e2e test builds its own engine. No test shares an LLM through a module- or session-scoped fixture, and many tests build two (TP1 and TP2, fp16 and fp8, APC and plain, transformers and native). Most of the time goes into build and compile, not into the checks.
  • The same model is built over and over. Four test_compile tests and three test_kernel_cache cases each build the same compiled micro-g3.3 config, and the two compiled Ministral-14B tests share one config.
  • Full-size models are used where a small one would do. Most multimodal tests only check text.strip(), yet they load 14–26B of weights.
  • Two legs run one test each and set the wall clock. smoke-0 runs only the gemma-4 image test (41.5 min) and distributed-0 only the TP2 image test (47 min). The other legs take about 28–31 min.

Order: Phase 1 merges tests and truncates the parity models; every assertion stays, so the risk is low. Phase 2 swaps in smaller models and tighter shapes, each measured before and after. Phase 3 changes the CI plumbing, once the long legs are gone.

Phase 1 · Consolidate and truncate (no coverage change)

E1 · One Ministral-14B compiled engine for the text-only and image checks

~25 minEffort Stests/e2e/test_multimodal.py

Change: merge test_single_image_prompt_produces_output[compiled] (26.5 min) and test_warmup_covers_text_only_token_embedding_on_multimodal_model (24.9 min), which call _generate with the same config. Let _generate take a list of prompt batches and run them on one LLM, the text-only prompt first and then the image prompt.

ProsBoth checks stay, and one full 14B build and compile goes away.
ConsThe image test doesn't arm SPYRE_COMPILE_GUARD=error today. If the Pixtral tower compiles on first use, the merged test fails. Either run the text-only step under warn, or confirm first that the tower is warmed.

E2 · Truncate gemma-4 in the TP2 parity test

27.2 → a few minEffort S/Mtests/e2e/test_distributed_tp2.py

Change: in the gemma-4-26B-A4B-text param of test_tp2_compiled_llm_generate_matches_tp1, pass hf_overrides={**GEMMA4_TEXT_BACKBONE_OVERRIDE, "text_config": {"num_hidden_layers": 4}}. Keep at least one sliding-window layer and one full-attention layer.

ProsTP1 vs TP2 still compares like with like: both sides are truncated the same way and use real weights. MoE and all-reduce stay covered.
ConsMerging the override may need nested-dict handling. Move the full-depth run to trunk.

E3 · Drop or truncate one gemma-4 row in test_compile

~10–13 minEffort Stests/e2e/test_compile.py

Change: keep gemma-4-26B-A4B-text (MoE) in test_basic_llm_inference and drop gemma-4-31B-text (dense). The alternative is to truncate both to a few layers and regenerate their reference strings.

ProsQuick win: a one-line change.
ConsOnly the quality gate would cover the dense gemma-4 decoder, and that gate isn't in the integration tier (see audit C1).

E4 · Fold the compile-guard test into test_basic_llm_inference

~3 minEffort Stests/e2e/test_compile.py

Change: test_warmup_covers_every_compile_a_request_needs uses the same model and shapes as the [micro-g3.3] row and differs only in the guard. Delete it and set SPYRE_COMPILE_GUARD=error in _assert_compiled_output for every row.

ProsThe warmup guard then also covers fp8, gemma-3 and gemma-4, so coverage grows.
ConsA gemma row may fail on a real warmup gap. That's useful signal, but the gap may need a fix before this lands.

Phase 2 · Smaller models and tighter shapes (measure first)

E5 · gemma-4 vision: truncated layers and dummy weights

up to ~40 of 52 minEffort Mtests/e2e/test_multimodal.py

Change: in test_gemma4_single_image_prompt_produces_output (41.5 min compiled, 10.7 min eager), add load_format="dummy", SamplingParams(ignore_eos=True), and hf_overrides that lower num_hidden_layers for both the text model and the vision tower. This is safe because the test only checks that output isn't empty.

ProsThe run no longer reads 26B of weights from the shared HF cache, and warmup has fewer graphs to build. The tower, projector and MoE code paths are unchanged.
ConsCompile time scales with the number of distinct graphs, not the number of layers, so count graphs before and after. Dummy weights can produce NaN, so keep the check at "non-empty".

E6 · Truncate or move the TP2 image parity test

up to ~47 min (longest leg)Effort Mtests/e2e/test_distributed_tp2.py

Change: test_tp2_compiled_image_prompt_matches_tp1 builds the 14B twice. Either cut the decoder and vision layers through hf_overrides (the test uses config_format="mistral", so check that the overrides reach params.json), or move it to trunk.

ProsRemoves the longest leg in the tier, and the distributed pool frees up first.
ConsNobody has tested overrides on a mistral-format config yet. If the test moves to trunk, TP vision bugs only surface after merge.

E7 · Tighten warmup sizes to what each test's prompts need

~2–5 min per testEffort S each
  • test_multimodal.py: lower MAX_MODEL_LEN from 512 to 256 for the Pixtral rows. test_distributed_tp2.py already serves the same 176×176 image at 256.
  • test_granite_vision.py: sets max_model_len=4096 with no compile_sizes, so warmup covers every bucket up to 4096. Pin both to the largest prompt (the 672 px multi-tile image) plus 16.
  • test_prefix_caching.py: max_model_len=512 with four engines per mode. Set it to the shared prefix plus the question plus 16.
ProsWarmup records fewer KV × query buckets. Each change is one line.
ConsA size that's too tight fails loudly (compile-guard error or an over-length rejection), so mistakes are easy to spot. Some files may save little.

E8 · Share one engine across the same-shape KV-determinism tests

~4 minEffort Stests/e2e/test_kv_cache_determinism.py

Change: test_logprobs_do_not_depend_on_earlier_requests and ..._in_a_batch both use max_model_len=256 and a 128-token prefill. Give them one module-scoped engine fixture with compile_sizes=[128, _BATCH_NUM_SEQS, 1], shut down at module teardown.

ProsSets up a pattern that other files can reuse.
ConsModule-scoped engines are new in this repo. The fixture must release the card reliably, since uses_subprocess tests rely on per-test teardown. State can also leak from one test into the other.

E9 · Reuse the parity baseline in test_vllm_spyre_next

~2–3 minEffort S

Change: test_basic_model_load builds a third eager micro-g3.3 engine only to assert len(text) > 0. Assert instead on the native output IDs that test_transformers_matches_native already produces, or just delete the test (see audit C4).

ProsOne engine fewer, and the remaining check compares real content.
ConsTies two files' tests together. Deleting the test is simpler.

Phase 3 · CI plumbing

E10 · Fast-fail first stage (R6)

Saves most of a broken runEffort S/M.github/workflows/_test_matrix.yaml

Change: run the non-e2e tests (~57 min) in one shard first, and make the e2e shards depend on it with needs:.

ProsWhen a torch-spyre PR breaks things, every shard fails together. With this stage it costs about 1 runner-hour instead of about 8.7.
ConsA passing run takes longer by the length of the first stage.

E11 · Rebalance shards once E1–E6 land

Wall clock and cards heldEffort SMakefile, _test_matrix.yaml

Change: run the rebalance-test-shards skill. Once the two single-test legs are gone, SMOKE_SHARDS=11 and DIST_SHARDS=3 can shrink.

ProsFewer Spyre cards allocated per run, and a shorter tail.
Constests/test_sharding.py has to stay in lockstep with the matrix. Do this last, once the durations have settled.

Not in scope here

  • Removing or demoting tests (xfails, eager duplicates, upstream duplicates): axis 2.
  • Which tiers run for which trigger: axis 3.
  • Reusing compiled artifacts across runs: axis 4. It adds to the savings here: fewer distinct graphs also means fewer cache entries.
