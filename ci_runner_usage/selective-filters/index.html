Axis 3 · Selective filters

Status: draft, ready for review. Part of the CI runner usage effort. Data: the integration-tier JUnit for run 41363344874 and main at 79f9659c (Nov 2, 2026).

1. Reduce execution time 2. Test audit 3. Selective filters 4. Compile cache

Summary

  • The integration tier was meant to be light. It's the default for the upstream-dependency dispatch from torch-spyre, and the Makefile calls it "the smoke suite: fast per-op unit tests only". Today it costs ~8.7 runner-hours a run, and ~87% of that is ~60 end-to-end model tests.
  • The cause is how tests get in. The tier is opt-out: every test runs unless its marker is on an exclude list. So each new e2e test lands in the integration tier by default, whatever it costs.
  • attention_smoke (#1190) already does the opposite: a hand-picked marker opts 11 of 588 attention cases into the tier, in one ~9-minute job.
  • Proposal: one opt-in marker, e2e_smoke, on a hand-picked set of e2e rows, sharded so each job runs in ~20 minutes. The integration tier's e2e jobs then run exactly pytest -m e2e_smoke, with no exclusion lists and no tier-dependent expressions. The audited pick has 26 cases and costs ~90 pytest-minutes, against ~391 today. It includes Ministral multimodal (two images, eager), one end-to-end MoE model (gemma-4-26B-A4B text, compiled) and five TP=2 cases rather than one. That takes an integration run from ~8.7 to ~4.4 runner-hours (before/after charts). Unit tests and attention smoke stay as they are, and trunk keeps running everything.
  • Regression follows the same pattern: regression = integration + a small opt-in regression_extra set, ~5.6 instead of ~14 runner-hours per PR run (regression proposal).
  • Admission is governed by policy, not tooling: written criteria, a 90-minute budget with a swap rule, and a rule in AGENTS.md pointing at it (admission policy). No CI guard or manifest: timings vary too much with cache warmth for a hard limit to be reliable.

The precedent: attention_smoke

Before #1190 (merged Oct 8, 2026), torch-spyre PRs exercised zero attention cases. Every attention matrix job was tagged unit regression trunk. The full suite can't be partly tagged either: tests/test_sharding.py::test_matrix_shard_blocks_within_a_suite_are_uniform requires every shard of a suite to share test_types. #1190 got around that without touching the sharded suite:

  1. An opt-in marker on a few parametrize rows. These are in tests/attention/test_spyre_attn.py and test_spyre_head_major_attn.py, covering token-major + head-major, eager + compiled, and decode / prefill / batched-decode. For example: 
    pytest.param([(1, 512)], id="decode(q=1,kv=512)", marks=pytest.mark.attention_smoke),
pytest.param([(1, 256)], id="decode(q=1,kv=256)"),
  2. The marker registered in pyproject.toml, stating its purpose: "small representative decoder-attention subset (also marked attention); its own 1-card job carries attention coverage into the integration tier".
  3. A Makefile target: test-attention-smoke: MARK_OVERRIDE='attention_smoke and not (distributed or upstream)'.
  4. One unsharded matrix job in _test_matrix.yaml with test_types: integration only.

The tagged cases also keep their attention marker, so they still run in the full shards under every other tier: nothing loses coverage. The opt-in set is a copy, not a move.

The same choice is already made elsewhere. probe and model_quality are excluded from integration, and the comment in _test_matrix.yaml says the quality gate stays out "since every case compiles a product model". What's missing is that same choice for the e2e tests in the smoke shards.

Why the tier drifted

The smoke expression only excludes. So every file added to tests/e2e/ joins the integration tier unless its author knows to mark it out. Since mid-September that has included Ministral-3-14B multimodal (#736), the model-output checks (#723), granite-vision (#944), the kernel cache (#1216), FP8 KV cache (#1146), TP4 (#729), prefix caching (#727) and spec-decode (#1440). The smoke suite went from 8 shards (Sep 4, #719) to 11 (Oct 19, #1312). Each shard is ~31–38 minutes on a dedicated card.

Proposal: one opt-in marker, e2e_smoke

This is the same shape as attention_smoke: a marker on hand-picked rows, one Makefile target, its own integration-only matrix entries. The whole selection is the marker:

pytest -m e2e_smoke

No path-based helper marker, no not (…) exclusion list, and no expression that changes with the tier. Whatever carries the marker runs; nothing else from tests/e2e/ does. To see exactly what a torch-spyre PR will pay for, run pytest -m e2e_smoke --collect-only -q.

1 · Register the marker and tag rows

In pyproject.toml, next to attention_smoke:

"e2e_smoke: small representative e2e subset (tests/e2e/); its own integration-only jobs carry e2e coverage into the integration tier, which the full e2e suite is excluded from",

Then tag rows, as #1190 did, either on whole functions or on single pytest.param rows:

@pytest.mark.e2e_smoke
def test_two_image_prompt_produces_output(): ...

pytest.param("ibm-ai-platform/micro-g3.3-8b-instruct-1b", None, id="micro-g3.3", marks=pytest.mark.e2e_smoke),

The tagged rows keep their existing markers (multimodal, distributed, …). So they still run inside the full smoke and distributed shards under unit and trunk. Like attention_smoke, the opt-in set is a copy, not a move.

2 · The audited pick

26 cases, ~90 pytest-minutes (62.3 on 1-card, 27.6 on 2-card). How it was chosen:

  • Vision via test_multimodal.py. Its two cheap rows exercise Ministral-3-14B's Pixtral path, which nothing else in the tier covers end to end: conv patch embed, vision RoPE, padded SDPA, patch merger, projector norm, decoder. test_two_image_prompt_produces_output (4.6 min) is the only case where the cu_seqlens block-diagonal mask must block attention across images. test_single_image_prompt_produces_output[eager] (4.5 min) runs the path eagerly. The compiled Pixtral graphs are already in the tier through tests/models/test_pixtral_vision.py::test_compiled_pipeline_matches_upstream_on_spyre, a 1–2 min model-level test in the unit shards. So between them the integration tier covers Pixtral eager end to end and compiled at the module level. That makes these a better fit for the vision slot than granite-vision, which is left out.
  • TP=2 as a real set. Five cases on the 2-card runner, all on micro-g3.3: construction, eager parity, compiled parity (the in-graph all-reduce), FP8 KV cache under TP, and the shared kernel cache at TP=2. Together ~28 min.
  • Cheap single-card cases that each cover a distinct path in ≤ 2.3 min: compiled encoder pooling buckets, a head_size=32 encoder (the opaque-attention fallback), token classification, and the head-dim/intermediate-size padding passes.
  • MoE end to end via gemma-4-26B-A4B text, compiled. It's the only MoE model in the suite. The on-card MoE module tests (tests/models/test_gemma4_moe.py, test_moe_bias.py) stay in the unit-level jobs and cover the gathered and all-expert kernels against a dense reference at TP1/2/4. Only this case exercises compiled block graphs with a MoE layer inside, warmup, and the switch between the two kernels mid-request. At 13.2 min it's over the ~10-minute guideline: it's the named exception for MoE, and it takes the second-decoder-family slot from gemma-3-1b-it.
  • Excludes anything else that builds a 14B+ model compiled (Ministral compiled, gemma-4 31B, the gemma-4 26B TP=2 parity case, the TP=2 image test), the xfailing test_kernel_cache[tp1-fresh], and the duplicate eager/compiled twins.

3 · Makefile targets and matrix entries

Each new target is a plain marker expression, the same way test-attention-smoke is:

E2E_SMOKE_SHARDS ?= 3
test-e2e-smoke-shard:  ## integration-tier e2e, 1 card (E2E_SMOKE_SHARD_ID=i)
	$(MAKE) run-one MARK_OVERRIDE='e2e_smoke and not distributed' \
	  PYTEST_ARGS='$(PYTEST_ARGS) --e2e-smoke-shards=$(E2E_SMOKE_SHARDS) --e2e-smoke-shard-id=$(E2E_SMOKE_SHARD_ID)' \
	  JUNIT_XML=$(JUNIT_XML)

E2E_SMOKE_DIST_SHARDS ?= 2
test-e2e-smoke-dist-shard:  ## integration-tier e2e, 2 cards
	$(MAKE) run-one MARK_OVERRIDE='e2e_smoke and distributed' \
	  PYTEST_ARGS='$(PYTEST_ARGS) --e2e-smoke-dist-shards=$(E2E_SMOKE_DIST_SHARDS) --e2e-smoke-dist-shard-id=$(E2E_SMOKE_DIST_SHARD_ID)' \
	  JUNIT_XML=$(JUNIT_XML)

The 1-card/2-card split is only about runner size, so the 1-card cases don't hold a second card. pytest -m e2e_smoke on a 2-card host still runs the whole set in one go. Both are sharded so each job runs in ~20 minutes when runners are free. The existing plugin partitioner does this unchanged: it runs after marker selection and balances on test-durations.json, so each suite just needs its --<suite>-shards pair registered in sharding.add_shard_options.

Admission policy for e2e_smoke

The marker is cheap to add, which is exactly how the opt-out tier grew. So admission is a decision made in review against written criteria and a budget, not a tag. There's deliberately no CI guard: test timings swing widely with compile-cache warmth, so a hard time limit would either flake or need slack wide enough to be useless. The policy and reviewers carry it. The same policy should cover attention_smoke, which has the same risk at a smaller scale.

What the tier is for

One question: does this torch-spyre (or RPM) change break a Spyre-specific path in spyre-inference? The tier is the check a torch-spyre PR pays for on every push. It isn't where correctness, accuracy or model coverage is proven; trunk and the quality gate do that, and keep running every e2e test. A test belongs here only if it's the cheapest way to answer that question for a path nothing else in the tier reaches.

Admission criteria (all must hold)

  1. Names a distinct path. The entry states the Spyre-specific path it covers: a kernel, lowering, layout, cache, padding pass or parallel mode. No current e2e_smoke entry may cover the same path. "Another model" is not a path; "the head_size=32 opaque encoder-attention fallback" is.
  2. Not already covered more cheaply. If a unit-level or model-level test that already runs in the integration tier (tests/custom_ops/, tests/models/, tests/attention/ via attention_smoke) reaches that path on card, don't admit. Example: compiled Pixtral graphs are covered by tests/models/test_pixtral_vision.py, so no compiled Ministral e2e case is needed for them.
  3. Cheapest representative. The smallest model that reaches the path (micro-g3.3, granite-embedding-30m; a truncated or dummy-weight config where one exists). One mode: compiled, unless the path is eager-only. One parametrize row, not the whole function. Short max_model_len and prompts.
  4. Small: about 10 minutes or less in a cold CI run (a compile-cache miss, which is what a torch-spyre PR sees), not a warm local rerun. The PR states the figure and where it came from, such as a CI run's JUnit or test-durations.json.
  5. Stable. Not xfail, no open flake issue, and green on the last 10 trunk runs (checked in ClickHouse). The tier gates other repos' PRs, so a flaky entry costs their authors, not just us.
  6. Fits the budget. The e2e_smoke total stays around 90 minutes, cold. Check it with pytest -m e2e_smoke --collect-only -q against the latest test-durations.json. If adding the case would go over, the PR also removes or shrinks another entry (the swap rule below). Raising the budget is a separate, explicit decision by the CI owners, never a side effect of an admission PR.

The swap rule

The budget is fixed, so admitting over it means removing something. The PR author proposes the swap, comparing the two entries' paths, cost and failure history, and the reviewer decides. Today's set uses ~90 of 90 minutes, so any new admission is a swap. That's deliberate.

Removal and review

  • Remove an entry when another entry or a cheaper unit-level test comes to cover its path, when it has grown well past the size limit and can't be brought back down, or when it goes xfail or flaky. Removing only drops the marker; the test keeps running in trunk.
  • Review the whole set quarterly with axis 2 (test audit). Re-check each entry's path is still distinct, and look at which entries actually caught a torch-spyre regression. A path that has never failed isn't removed for that alone; it's still the cheap guard on its path.

Proposal: the regression tier

regression runs on every push to our PRs and in the merge queue, at ~14 runner-hours a run (~5.6k h per two weeks, plus spyre-ci's own regression dispatches). It's meant to "test everything", but our lockfiles pin the stack, so most of those runs re-test an unchanged stack on a cold cache. We only control what each suite selects, not who triggers it, so the proposal changes the definition and nothing else.

regression = integration + one more opt-in marker, regression_extra. trunk stays "everything".

Beyond the integration tier

  • No PR labels for selection. Dispatches come from many internal repos as well as torch-spyre, and labels don't travel with them. What runs is chosen by the standardized test suite (unit, integration, regression, trunk) and nothing else. To get more than the integration tier, a caller asks for a bigger suite: a workflow_dispatch of integration-tests.yaml with test_type=regression already runs everything.
  • Keep the vocabulary. unit / integration / regression / trunk / perf are shared with torch-spyre and hf-adapters, and the Makefile rejects anything else. Everything here changes what integration selects in this repo, not the tier names, so no other repo or dispatcher needs to change.

Open questions

  • Is the pick right? In particular: gemma-4 vision has no e2e coverage in the tier (only tests/models/test_gemma4_mm.py at the module level). Should a gemma-4 case come back once axis 1 makes it cheap, e.g. with a truncated tower or dummy weights?
  • Budget number: 90 pytest-minutes is a guess. What turnaround do torch-spyre authors need from this check?
