Axis 3 · Selective filters and labels

Status: draft, ready for review. Part of the CI runner usage effort. Data: the integration-tier JUnit for run 41363344874 and main at 79f9659c (Nov 2, 2026).

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

  • The integration tier was meant to be light. It's the default for the upstream-dependency dispatch from torch-spyre, and the Makefile calls it "the smoke suite: fast per-op unit tests only". Today it costs ~8.7 runner-hours a run, and ~87% of that is ~60 end-to-end model tests.
  • The cause is how tests get in. The tier is opt-out: every test runs unless its marker is on an exclude list. So each new e2e test lands in the integration tier by default, whatever it costs.
  • attention_smoke (#1190) already does the opposite: a hand-picked marker opts 11 of 588 attention cases into the tier, in one ~9-minute job.
  • Proposal: apply the same opt-in pattern to the e2e tests with an e2e_smoke marker, so an e2e case runs in the integration tier only if it carries the marker. A first pick costs ~54 pytest-minutes, against ~390 today. That takes the tier to ~2.5–3 runner-hours a run, in line with R1 in the main report. Unit tests and attention smoke stay as they are, and regression/trunk keep running everything.

The precedent: attention_smoke

Before #1190 (merged Oct 8, 2026), torch-spyre PRs exercised zero attention cases. Every attention matrix job was tagged unit regression trunk. The full suite can't be partly tagged either: tests/test_sharding.py::test_matrix_shard_blocks_within_a_suite_are_uniform requires every shard of a suite to share test_types. #1190 got around that without touching the sharded suite:

  1. An opt-in marker on a few parametrize rows. These are in tests/attention/test_spyre_attn.py and test_spyre_head_major_attn.py, covering token-major + head-major, eager + compiled, and decode / prefill / batched-decode. For example: 
    pytest.param([(1, 512)], id="decode(q=1,kv=512)", marks=pytest.mark.attention_smoke),
pytest.param([(1, 256)], id="decode(q=1,kv=256)"),
  2. The marker registered in pyproject.toml, stating its purpose: "small representative decoder-attention subset (also marked attention); its own 1-card job carries attention coverage into the integration tier".
  3. A Makefile target: test-attention-smoke: MARK_OVERRIDE='attention_smoke and not (distributed or upstream)'.
  4. One unsharded matrix job in _test_matrix.yaml with test_types: integration only.

The tagged cases also keep their attention marker, so they still run in the full shards under every other tier: nothing loses coverage. The opt-in set is a copy, not a move.

The same choice is already made elsewhere. probe and model_quality are excluded from integration, and the comment in _test_matrix.yaml says the quality gate stays out "since every case compiles a product model". What's missing is that same choice for the e2e tests in the smoke shards.

Why the tier drifted

The smoke expression only excludes. So every file added to tests/e2e/ joins the integration tier unless its author knows to mark it out. Since mid-September that has included Ministral-3-14B multimodal (#736), the model-output checks (#723), granite-vision (#944), the kernel cache (#1216), FP8 KV cache (#1146), TP4 (#729), prefix caching (#727) and spec-decode (#1440). The smoke suite went from 8 shards (Sep 4, #719) to 11 (Oct 19, #1312). Each shard is ~31–38 minutes on a dedicated card.

Proposal: opt-in e2e_smoke

This is the same shape as attention_smoke, but applied inside the existing smoke and distributed targets rather than as a new job. That's because the e2e tests are already spread across the smoke shards.

1 · Mark what an e2e test is, automatically

Add an e2e marker applied at collection to everything under tests/e2e/, which is where every engine-building test already lives. This is the same pattern the plugin already uses to add upstream by path. A test can't forget it, so it doesn't rely on authors remembering.

# tests/conftest.py, inside the existing pytest_collection_modifyitems
if "tests/e2e/" in item.nodeid:
    item.add_marker(pytest.mark.e2e)

2 · Opt a small set in with e2e_smoke

Register e2e_smoke in pyproject.toml, worded like attention_smoke, and put it on hand-picked parametrize rows. A first pick that keeps compiled coverage of each model family torch-spyre can break:

3 · Use a different smoke expression for the integration tier only

Today every tier's smoke jobs run the same MARK_OVERRIDE. Give the integration tier one extra clause:

# smoke, integration tier
not (distributed or distributed_tp4 or upstream or attention or probe or model_quality)
  and (not e2e or e2e_smoke)

# distributed, integration tier
distributed and not (upstream or probe) and e2e_smoke

Keep it in the Makefile, which already owns the tier→marker mapping. Watch out: run-matrix-config calls make ${{ inputs.test_target }} without TEST_TYPE. It only exports the tier as SPYRE_TEST_TIER, for result tags, so a target can't branch on the tier today. Separate integration-only targets (below) avoid needing that at all.

The shard count has to differ by tier, which collides with the uniformity guard. The integration tier needs ~3 smoke shards and 1 distributed shard; regression still needs 11 and 3. Two options:

  • Separate integration-only targets and matrix entries (test-smoke-int-shard-N, SMOKE_INT_SHARDS), tagged test_types: integration. The existing smoke entries drop integration from their test_types. This matches #1190 exactly and passes test_matrix_shard_blocks_within_a_suite_are_uniform unchanged, because each suite stays uniform. It's the recommended option. Teach _makefile_shard_counts / _matrix_shard_ids in tests/test_sharding.py about the new suite, and the rebalance-test-shards skill along with them.
  • One target whose shard count depends on the tier. Fewer YAML entries, but it needs the planning job from R2, since a static matrix can't vary its length by an input. It also weakens the guard.

Note: the _test_matrix.yaml comment on the smoke block says it "MUST keep integration in this set" so the torch.compile e2e coverage doesn't silently vanish. With the split, that coverage moves to the e2e_smoke rows in the new integration-only entries. Update the comment and keep a guard for it (step 4).

4 · Guards, so the tier can't drift again

  • Never empty: a test asserting that -m "e2e_smoke" collects at least one compiled case per e2e_smoke-tagged family. Use pytester or a --collect-only run, the same way #1190 checked its 11 of 588.
  • Budget: a test that sums recorded durations (the pinned durations file the sharder already downloads) over the integration selection and fails above a set limit, e.g. 120 pytest-minutes. A new e2e_smoke tag then needs a conscious budget change, not just a shard bump.
  • Registry: e2e and e2e_smoke documented in pyproject.toml, and a line in CONTRIBUTING / CLAUDE.md: "new e2e tests are regression-only unless tagged e2e_smoke, and must fit the integration budget".

Beyond the integration tier

  • Opt back in on demand. A workflow_dispatch run of integration-tests.yaml can already pass test_type=regression to get everything. For our own PRs, a PR label (e.g. ci:full-e2e) could switch a PR run from a reduced set to full, via the same composite-action pattern as detect-integration-test-label. That only matters if axis 2 / R4 reduces regression on PR pushes.
  • Reuse the marker for the regression trim. Once e2e exists, moving heavy e2e from PR regression to trunk or the merge queue is another tier clause, not a new mechanism.
  • Keep the vocabulary. unit / integration / regression / trunk / perf are shared with torch-spyre and hf-adapters, and the Makefile rejects anything else. Everything here changes what integration selects in this repo, not the tier names, so no other repo or dispatcher needs to change.

Open questions

  • Is the e2e_smoke pick above right? In particular: is one compiled vision path (granite-vision) enough while the Ministral and gemma-4 tests are expensive, or should one of them come back once axis 1 makes it cheap?
  • Budget number: 120 pytest-minutes (~3 shards) is a guess. What turnaround do torch-spyre authors need from this check?
  • Labels on PRs vs. markers on tests: this page puts the filter on markers, since dispatched runs carry no PR labels we control. Is a PR-side override for our own PRs worth adding?
