Axis 4 · Compile cache

Investigation · Nov 3, 2026 (corrected the same day) · Data: every integration-tests.yaml dispatch by spyre-ci[bot], Oct 19 – Nov 1 (767 runs). Part of the CI runner usage effort, expanding R5.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

R5 asks three questions. This page answers two of them. How much would reuse within one torch-spyre PR save? Not much: most repeat triggers test a new commit. Is it safe to seed a run's cache from a different torch-spyre commit? No. The Inductor graph cache would hit, and its cached code is not guaranteed to work with the new commit. So a cache for dispatched runs must be keyed on the exact torch-spyre commit, which caps what it can save.

  • Cross-commit seeding is a crash risk. Inductor's FX-graph key hashes torch's own source and torch-spyre's graph-pass files, not torch-spyre's lowering, scheduler, wrapper codegen, op_spec.py or _C. A restored entry from another commit is a hit, and its cached wrapper code builds torch-spyre objects against the old API. That is the TypeError: … unexpected keyword argument crash the upgrade-torch-spyre skill warns about, or a silent mismatch when a field changes meaning. See safety.
  • Reuse within a PR alone isn't worth a cache rework. 80–135 h per 14 days is about 1% of the dispatched runner-hours.
  • The hours are in runs on a new torch-spyre commit. 2,160 h are pushes that changed torch-spyre, and 1,490 h are each PR's first run. A safe cache can't help those. Only the Spyre kernel layer could ever be reused across commits, and only after a torch-spyre key change (question 2).
  • Dispatches that aren't torch-spyre PRs reuse less than this page first said. Each dispatch builds its own image from the current torch-spyre main, which got 117 commits in the window, about 8 a day. Reuse comes only from bursts of dispatches landing on the same main commit, within a median of 1.5 h. With the exact commit and uv.lock matching, 122 runs (1,274 h) would have hit, worth ~640 h per 14 days at most. See below.
  • Separate finding: before #1353 (Oct 23), cancelled runs left test jobs running for up to 24 h. That's 317 jobs and about 2,980 h, or 30% of the window's dispatched test hours. Those hours are counted in the main report's 10.3k h figure. #1353 already fixes this, so the main report overstates the steady-state cost of the integration tier. All numbers on this page leave those jobs out.

Is it safe to seed the cache from another torch-spyre commit?

No, not for the whole cache. Kernel cache misses are acceptable; crashes and wrong results are not. The TORCHINDUCTOR_CACHE_DIR that nfs_compile_cache.py ships holds three kinds of entry, and they behave differently when the torch-spyre commit changes. Checked against torch-spyre c88b6d4 (Nov 3) and torch 2.13.0a0+gitcf30153.

This is the situation CI.md already describes for lockfile bumps: "the cache never falls back to an older key", because Inductor's graph key doesn't cover all of torch-spyre's lowering code. That rule has to apply to dispatched runs too. The upgrade-torch-spyre skill's mandatory rm -rf /tmp/torchinductor_* step exists because of this exact crash.

What a safe cache for dispatched runs looks like

  • Key on the exact stack. The torch-spyre version string, the hash of $LIB_VERSION_FILE, uv.lock and KEY_SALT. Within one key, share everything.
  • Across keys, share nothing except possibly the CPU .so files. Seeding those alone from main is the only cross-commit reuse that looks safe. It needs a separate tar, because today's deltas mix all three layers.
  • Never let a different-commit run read or write main's scope. The current gate (skip when use_prebaked_image, torch_spyre_ref or rpm_names is set) is the right default until the key above exists. Lifting it with today's lockfile key would hand torch-spyre PR runs main's graph cache, which is the unsafe case.
  • Make torch-spyre safe even if the key is wrong. If torch-spyre returned its version, or a hash of its whole source, from its pass uuid(), Inductor would refuse cross-commit graph entries on any host. That would also protect developers' local /tmp/torchinductor_* caches. It is a one-line change upstream and removes the crash class entirely.

Why the same commit gets triggered again

Among the 33 same-commit repeats, the earlier run had been cancelled in 18 cases and had failed in 3. In 24 of them, the spyre-inference main commit under test had also moved on. That only matters if uv.lock changed, so the key should hash our lockfile, not our commit. The median gap between two triggers of the same PR is 6 h. 36% of triggers come within 3 h of the previous one, which is usually long enough for an earlier shard to finish and save a delta.

Dispatches that aren't torch-spyre PRs

215 of the 767 dispatches don't come from a torch-spyre PR: 89 from our own PRs (regression tier), 74 with a PR hash I couldn't match, and 50 with no hash (scheduled, trunk and perf). Each one builds its own image from torch-spyre main as it was at that moment. I saw 741 distinct image labels across the 767 runs. In 160 of the 179 runs whose version I could read, torch-spyre was a main commit. main got 117 commits in the window, about 8 a day, so these runs only share a stack when several dispatches land on the same commit. They used 62 distinct versions: 25 were used once, and a repeated version's runs fell within a median of 1.5 h of each other.

Requiring the same uv.lock as well (13 distinct lockfiles in the window) leaves 122 runs and 1,274 h, so the saving is at most ~640 h per 14 days. It is still an upper bound: I couldn't check that the RPM set matched, and a run only helps the next one if a green shard finished first. The earlier version of this page said these runs share long-lived images and put the saving at ~950 h. That was wrong.

This is the only sizeable win a safe cache gets. It is fragile, because it depends on dispatches clustering within an hour or two of each other on one main commit. These runs never contain torch-spyre PR code, so no PR's kernels can leak into another's cache. They still must not read main's scope, because main's scope is keyed on our pinned torch-spyre, which differs from the image's. Today the pin is 0.6.0.dev417+master.gf8a09bb0 and the dispatch images run 0.6.0.dev418+head.gf34574a6.

What a correct key needs

  • torch-spyre version, exactly. Never a prefix or a "compatible" range (see safety). It is readable on the image without installing anything. The test job's Dump UV cache info step already prints the editable wheel name, e.g. torch_spyre-0.6.0.dev418+head.gf34574a6. A cheaper source is torch_spyre._version.__version__ on the cardless artifact_identity job.
  • RPM versions. The Spyre kernel key reads the deeptools and flex versions from $LIB_VERSION_FILE (/opt/ibm/spyre/components.txt), so that file's hash belongs in the key.
  • Our side. uv.lock as today, and the KEY_SALT.
  • Not the image id. 741 distinct image_id_* labels showed up in 767 runs. A label maps to one torch-spyre version, but 78 versions appeared under more than one label, so keying on the label would split hits that are really the same stack.

Next steps

  1. Upstream: make torch-spyre's pass uuid() include its version or a hash of its full source. This is the cheapest fix and closes the crash class on every host, CI or not. File it before any change that widens who reads the cache.
  2. Decide whether an exact-stack dispatch cache is worth building for ~700–800 h per 14 days. That's ~640 h from main-commit bursts plus ~80–135 h from repeats within a PR. It needs a stack key, a dispatch scope and a ts-<pr_url_hash> scope, and neither may read main. It is less than R1 (trimming the tier) saves, and the two compound, so R1 comes first.
  3. Measure the CPU .so layer. Time one cold shard with and without only the *.so files pre-seeded. If it really is several minutes per job, seeding just that layer from main is the one safe reuse across commits, and it applies to every dispatch.
  4. Question 2 (Spyre kernel reuse across commits) only if torch-spyre wants it. It needs a torch-spyre key built from content rather than the version, plus the tp1-fresh fix. Even then, only the Spyre kernel layer could be shared, never the graph cache.

Method and caveats

How the data was gathered
  • Runs: every workflow_dispatch run of integration-tests.yaml by spyre-ci[bot] created Oct 19 – Nov 1 (767 runs), listed in 6-hour windows.
  • PR attribution: the pr_url_hash printed by each run's Log upstream dependant tool regression trigger job, matched against sha256 of https://github.com/torch-spyre/<repo>/pull/<n> for every repo in the org and n < 12,000. 255 of 302 distinct hashes matched.
  • Stack: the torch-spyre version is parsed from the editable wheel name in a test job's log (the first green shard, otherwise the first that ran). 88 runs (979 h, mostly short perf failures and early cancellations) have none.
  • "Kernel-relevant change" means the GitHub compare between consecutive commits of the same PR touches torch_spyre/, csrc/, third_party/, cmake/, C/C++ sources, setup.py, pyproject.toml or CMakeLists.txt.
  • Hours: the summed duration of each run's build and run tests jobs, excluding any single job over 2 h (the pre-#1353 cancelled jobs). Setup jobs such as sampling kernels and artifact identity are left out because the cache can't affect them.
  • Safety analysis: read from source, not tested. Torch-spyre c88b6d4: _inductor/passes.py, _inductor/__init__.py, _inductor/wrapper.py, execution/kernel_cache.py. Torch cf30153: _inductor/codecache.py (torch_key, FxGraphHashDetails).
  • Caveat: treating a hit as worth half the run assumes the whole run hits. A partial hit is worth less. Repeated triggers are also partly an artifact of cancel-in-progress: a run cancelled before any shard finished saves nothing for the next one.

Per-run data for the torch-spyre PR runs (PR, run id, torch-spyre version, image, class, test-job hours): data/compile-cache-within-pr.json.
