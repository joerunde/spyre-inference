Axis 4 · Compile cache

Investigation · Nov 3, 2026 · Data: every integration-tests.yaml dispatch by spyre-ci[bot], Oct 19 – Nov 1 (767 runs). Part of the CI runner usage effort, expanding R5.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

R5 asks three questions. This page answers the first one: how much would reuse within one torch-spyre PR save? Not much. Reuse within a PR only helps when the same torch-spyre commit is tested twice. Most repeat triggers come after a new push, and both cache layers include the torch-spyre version in their key, so a new commit always misses.

  • Reuse within a PR alone isn't worth a cache rework. About 135 h per 14 days is roughly 1.4% of the dispatched runner-hours.
  • The hours are in runs on a new torch-spyre commit. 2,160 h are pushes that changed torch-spyre, and 1,490 h are each PR's first run. The cache can only help those if kernels survive a torch-spyre version change. That is question 2, and it is the next thing to measure.
  • Unexpected larger win: dispatches that aren't torch-spyre PRs. These are mostly the regression tier on our own PRs. They run on standing images whose torch-spyre is a main commit, and most of them reuse a stack an earlier run already tested. About 1,900 test-job hours would have hit an exact-stack key, worth ~950 h per 14 days. See below.
  • Separate finding: before #1353 (Oct 23), cancelled runs left test jobs running for up to 24 h. That's 317 jobs and about 2,980 h, or 30% of the window's dispatched test hours. Those hours are counted in the main report's 10.3k h figure. #1353 already fixes this, so the main report overstates the steady-state cost of the integration tier. All numbers on this page leave those jobs out.

Why the same commit gets triggered again

Among the 33 same-commit repeats, the earlier run had been cancelled in 18 cases and had failed in 3. In 24 of them, the spyre-inference main commit under test had also moved on. That only matters if uv.lock changed, so the key should hash our lockfile, not our commit. The median gap between two triggers of the same PR is 6 h. 36% of triggers come within 3 h of the previous one, which is usually long enough for an earlier shard to finish and save a delta.

How much a hit saves

To estimate this, I compared smoke-shard durations between cold and warm runs since the NFS cache landed (#1323, Oct 23). The cold side is dispatched integration runs. The warm side is test_each_commit runs on Oct 24–31 whose shard log reports compile cache: restored … files (168 of 181 runs). The smoke shards use the same marker set in both tiers.

The larger win: dispatches that aren't torch-spyre PRs

215 of the 767 dispatches don't come from a torch-spyre PR: 89 from our own PRs (regression tier), 74 with a PR hash I couldn't match, and 50 with no hash (scheduled, trunk and perf). They run on standing images. In 160 of the 179 runs whose version I could read, torch-spyre was a main commit, so many runs share one stack:

Here "the same stack" matches on the torch-spyre version only, across any earlier dispatch. That is an upper bound, because the RPM set and our uv.lock also have to match. Even so, keying these runs on the image's stack and giving them a shared dispatch scope could save ~950 h per 14 days, about 7× the reuse within torch-spyre PRs. These runs were never torch-spyre PR code, so the safety concern from R5 (kernels from a torch-spyre PR leaking into our cache) does not arise.

What a correct key needs

  • torch-spyre version. It is readable on the image without installing anything. The test job's Dump UV cache info step already prints the editable wheel name, e.g. torch_spyre-0.6.0.dev418+head.gf34574a6. A cheaper source is torch_spyre._version.__version__ on the cardless artifact_identity job.
  • RPM versions. The Spyre kernel key reads the deeptools and flex versions from $LIB_VERSION_FILE (/opt/ibm/spyre/components.txt), so that file's hash belongs in the key.
  • Our side. uv.lock as today, and the KEY_SALT.
  • Not the image id. 741 distinct image_id_* labels showed up in 767 runs. A label maps to one torch-spyre version, but 78 versions appeared under more than one label, so keying on the label would split hits that are really the same stack.

Next steps

  1. Question 2, measured on hardware. Fill a kernel cache with torch-spyre commit A. Install the next commit, B, of the same PR, and rerun one smoke shard with only SPYRE_KERNEL_CACHE shared. For a fair test, B's version string should be forced to match A's, since both keys contain it. Count the kernel hits. If most kernels hit, the 1,900 + 1,486 h of new-commit runs become reachable, but only with a source-hash key in torch-spyre. That needs a torch-spyre change and the tp1-fresh key fix.
  2. Do the stack-keyed cache for non-torch-spyre-PR dispatches first. It is the cheapest change with the largest measured win. It needs a stack key and one read+write dispatch scope, and it must not touch main.
  3. Reuse within a torch-spyre PR comes with that change almost for free. Once there is a stack key, a ts-<pr_url_hash> scope is a few lines. Keep it read+write only for its own PR, so torch-spyre PRs never write into a scope another PR reads.

Method and caveats

How the data was gathered
  • Runs: every workflow_dispatch run of integration-tests.yaml by spyre-ci[bot] created Oct 19 – Nov 1 (767 runs), listed in 6-hour windows.
  • PR attribution: the pr_url_hash printed by each run's Log upstream dependant tool regression trigger job, matched against sha256 of https://github.com/torch-spyre/<repo>/pull/<n> for every repo in the org and n < 12,000. 255 of 302 distinct hashes matched.
  • Stack: the torch-spyre version is parsed from the editable wheel name in a test job's log (the first green shard, otherwise the first that ran). 88 runs (979 h, mostly short perf failures and early cancellations) have none.
  • "Kernel-relevant change" means the GitHub compare between consecutive commits of the same PR touches torch_spyre/, csrc/, third_party/, cmake/, C/C++ sources, setup.py, pyproject.toml or CMakeLists.txt.
  • Hours: the summed duration of each run's build and run tests jobs, excluding any single job over 2 h (the pre-#1353 cancelled jobs). Setup jobs such as sampling kernels and artifact identity are left out because the cache can't affect them.
  • Caveat: treating a hit as worth half the run assumes the whole run hits. A partial hit is worth less. Repeated triggers are also partly an artifact of cancel-in-progress: a run cancelled before any shard finished saves nothing for the next one.

Per-run data for the torch-spyre PR runs (PR, run id, torch-spyre version, image, class, test-job hours): data/compile-cache-within-pr.json.
