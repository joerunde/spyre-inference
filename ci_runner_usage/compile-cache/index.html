Axis 4 · Compile cache

Report · Nov 3, 2026 · Conclusion: don't extend the compile cache to dispatched runs. Data: every integration-tests.yaml dispatch by spyre-ci[bot], Oct 19 – Nov 1 (767 runs). This closes R5 of the CI runner usage report.

1. Reduce execution time 2. Test audit 3. Selective filters / labels 4. Compile cache

Summary

R5 proposed letting dispatched integration runs, mostly torch-spyre PRs, use the NFS compile cache, since most of their time goes on compiling. A cache hit really does halve a run. But no workable cache gets hits on these runs:

  • Across torch-spyre commits it is unsafe. Inductor's FX-graph cache would hit on entries from an earlier torch-spyre commit, because its key doesn't cover torch-spyre's lowering, codegen or runtime API. The cached code can then crash at model load or quietly run the wrong kernel. The Spyre kernel cache can't hit across commits at all. Details.
  • Within one commit there is almost nothing to reuse. The cache would have to be keyed on the exact stack, and nearly every dispatch tests a new one. torch-spyre PRs push a new commit before almost every trigger, and every other dispatch builds its image from a torch-spyre main that moves about 8 times a day. Details.
  • An exact-stack cache would mostly store dead data. It would have made 497 keys in 14 days, and only 69 would ever have been read. A cold run writes about 5 GB of deltas. Details.

Recommendation: keep today's behaviour. Dispatched runs skip the cache (the restore step is gated off when use_prebaked_image, torch_spyre_ref or rpm_names is set) and compile cold. That is correct, not a bug. The savings for this tier have to come from compiling less: R1 (trim the tier) and R3 (cheaper multimodal tests). Two small follow-ups remain:

  • Ask torch-spyre to close the unsafe key. If torch-spyre's pass uuid() returned its version, or a hash of its whole source, Inductor would refuse cross-commit graph entries everywhere. Today only our lockfile key protects CI, and nothing protects developers' local /tmp/torchinductor_* caches, which is why the upgrade-torch-spyre skill makes you delete them. Details.
  • Possibly reuse Inductor's CPU .so/.o files. Their key doesn't depend on torch-spyre or the RPMs, so they might be safe to share with every run. It's unmeasured and left for later. Details.

Separate finding. Before spyre-inference#1353 (Oct 23), cancelled runs left test jobs running for up to 24 h: 317 jobs, about 2,980 h, or 31% of the window's dispatched test-job hours. The main report's ~10.3k h for this workflow includes them, so it overstates the tier's ongoing cost. #1353 fixed it. Every figure on this page leaves those jobs out.

How the cache works today

Each test job gets its own TORCHINDUCTOR_CACHE_DIR and runs with SPYRE_KERNEL_CACHE=1. .github/scripts/nfs_compile_cache.py seeds that directory from /storage-1/spyre-inference/.cache/compile/<scope>/<arch>/<key>/. When the job finishes green, it saves the files it added as its own delta tar. The key is a hash of uv.lock and spyre-rpms.lock. Pushes to main and the merge queue write the main scope. A PR writes pr-<N> and reads that scope, then main. The restore step in .github/actions/run-matrix-config/action.yml is skipped for dispatched runs: they use a per-dispatch image whose torch-spyre and RPMs our lockfiles don't describe. Background is in CI.md under "Compile cache".

The cache directory holds three kinds of entry. They behave differently when torch-spyre changes, so the safety analysis below takes them one at a time.

Why cross-commit reuse is unsafe

A cache miss costs time, but a cache hit on stale code can crash a run or silently produce the wrong kernel. The table shows what each layer's key covers and what happens when the cache was written by one torch-spyre commit and read by another. This comes from reading the code, not from running it: torch-spyre c88b6d4 (Nov 3) and torch 2.13.0a0+gitcf30153, the version in uv.lock. The relevant excerpts are saved in source-excerpts/.

This is the rule CI.md already applies to lockfile bumps: "the cache never falls back to an older key", because Inductor's graph key doesn't cover all of torch-spyre's lowering code. The same crash is the reason the upgrade-torch-spyre skill's mandatory rm -rf /tmp/torchinductor_* step exists. Any scheme that seeds a run from another torch-spyre commit, such as reading main's scope or using a relaxed "compatible version" key, carries that risk on every hit.

The upstream fix

torch-spyre's pass pipelines could return torch_spyre._version.__version__, or a hash of every file in the package, from uuid(). Inductor would then refuse graph entries from another commit on every host, in CI or not. This doesn't make anything faster; it turns a crash or a wrong result into a cache miss. It is worth filing with torch-spyre whatever happens to the rest of this page.

Why same-stack reuse is too small

A safe cache for dispatched runs has to be keyed on the exact stack: the torch-spyre version string, the RPM set and uv.lock. It only helps when a later dispatch tests the same stack, and only once an earlier run's green shard has saved a delta. That rarely happens.

Other dispatches: short bursts on a moving main

The other 215 dispatches come from our own PRs (89, regression tier), PR hashes I couldn't match (74), runs with no hash (50, scheduled, trunk and perf) and hf-adapters (2). Each builds its own image: 740 distinct image ids appeared across 767 runs. For 160 of the 179 runs with a readable version, the torch-spyre commit was a main commit. main got 117 commits in the window. These runs used 62 torch-spyre versions, 25 of them only once. When a version did repeat, its runs fell within a median of 1.5 h of each other: bursts of dispatches on one commit, not a stack that stays put.

Allowing a hit from any earlier dispatch with the same torch-spyre commit and uv.lock (13 distinct lockfiles in the window), 122 runs (1,274 h) would have found an earlier green delta. That is worth ≤ ~640 h per 14 days. It's an upper bound: I couldn't confirm the RPM sets matched, and the hits depend on dispatches bunching within an hour or two. These runs still couldn't read main's scope, which is keyed on our pinned torch-spyre. Today that pin is 0.6.0.dev417+master.gf8a09bb0, while the dispatch images run 0.6.0.dev418+head.gf34574a6.

What an exact-stack cache would cost

  • Keys that go stale immediately. An exact-stack key (the torch-spyre version plus uv.lock) would have produced 497 keys in 14 days. 427 of them belong to a single run, and only 69 would ever have been read.
  • Large deltas. The two cold test_each_commit runs I measured each wrote about 5.1 GB across 41 shard deltas: about 137k files and 9.7k Spyre kernels. An integration run has 15 test jobs, so maybe 2 GB, which comes to roughly 1 TB of NFS writes per 14 days, mostly never read (data).
  • Cost on every run. Every green job tars and uploads its delta whether anyone reads it or not. The nightly cleanup (compile_cache_cleanup.yaml) only caps the disk space afterwards.
  • Small return. At most ~700 h per 14 days (≤ 640 h from bursts plus ~80 h within PRs), less than R1 alone saves. R1 also shrinks it further, because a trimmed tier compiles less.

Left to investigate: reusing the CPU .so/.o files

This is the one layer that might be safe to share across torch-spyre and RPM changes, so it could serve every run, dispatched runs included. It's unmeasured, so it's recorded here and not recommended. The reasoning comes from reading CppCodeCache.load_async and _worker_compile_cpp in torch's codecache.py (excerpt):

  • The cache is content-addressed. The key is a hash of the generated C++ and the full compiler command line. A cold compile regenerates the C++, hashes it and skips gcc if the target file already exists. Changed code gets a new path, so in the worst case it misses; it never loads stale code. torch-spyre doesn't generate these kernels, and the RPMs don't feed into them.
  • The key must still include torch, arch and ISA.
    • Torch's headers enter the command line by path, not by content, so the torch version belongs in our key. uv.lock has had 2.13.0a0+gitcf30153 since August. I haven't checked whether the dispatch images match.
    • Builds use -march=native but torch keys them on the ISA class only. That's the SIGILL caveat already in CI.md.
    • The gcc version isn't in torch's key. That's low risk, because the Python-binding kernels are built with include_pytorch: False.
  • The .o files have to ship too. _worker_compile_cpp rebuilds any missing intermediate target even when the linked .so exists, and that compile is the expensive step. The tar would hold only *.so and *.o, never fxgraph/, aotautograd/, inductor-spyre-cache/ or wrapper .py files.
  • Absolute paths could make every lookup miss. Include directories are part of the hash. If our jobs compile against torch under one venv path and dispatched jobs under another, nothing will hit. Nothing breaks either. One log from each tier showed the same /home/senuser/.venv/…/torch/include, but that's a single sample.
  • Storage isn't a concern. CI.md puts this layer at under 10 MB, and its key would change only with torch. One cache written by main and the merge queue and read by everyone would do.

To decide later: time one cold smoke shard with and without only the *.so/*.o files pre-seeded, and confirm the include paths match on a dispatched job. CI.md says rebuilding these takes "several minutes per job". If the gain turns out to be a minute or two per shard, not worth the extra moving part, this axis is closed.

Definitions and caveats
  • Test-job hours are the summed duration of a run's build and run tests jobs. Any single job over 2 h is left out; those are the jobs that kept running after a cancel before #1353. Setup jobs are left out because the cache can't affect them.
  • Warm means an earlier run with the same key had a test shard finish green before this run was created. Only green jobs save a delta.
  • Kernel-relevant change means the compare touches torch_spyre/, csrc/, third_party/, cmake/, C/C++ sources, setup.py, pyproject.toml or CMakeLists.txt.
  • Stack is read from the editable wheel name in a test job's Dump UV cache info step. 88 runs (mostly short perf failures and early cancels) have none. The RPM set isn't recorded, so every same-stack count on this page is an upper bound.
  • Not tested on hardware. The safety analysis is from reading the source. The .so section is a hypothesis.
