Scope

Most of the integration tier's wall time is spent compiling models, not running them. This axis covers getting the NFS-backed inductor/kernel compile cache to actually hit on the runs that currently compile cold.

  • Why dispatched (prebaked-image) runs skip the cache today: the restore step is gated off whenever use_prebaked_image, torch_spyre_ref or rpm_names is set, and the cache key (hash of uv.lock + spyre-rpms.lock) doesn't describe a prebaked image's stack anyway.
  • Keying the cache on the image's actual installed torch-spyre version/commit and RPM versions instead of our lockfiles.
  • Whether the Spyre kernel cache can survive a torch-spyre bump (depends on whether generated kernel source is stable across commits) — tied to the known test_kernel_cache[tp1-fresh] xfail.
  • Safety: dispatched (torch-spyre PR) runs should restore read-only so they can't poison the cache our own PRs read from.

Relevant existing findings

From the main report (§7 R5): this applies to roughly 10k runner-hours per 14 days of dispatched runs, essentially all of which compile cold today. Relevant files: .github/actions/run-matrix-config/action.yml, .github/scripts/nfs_compile_cache.py, tests/e2e/test_kernel_cache.py.

Open questions

  • Is cross-torch-spyre-version kernel reuse realistic, or should the win be scoped to same-key reuse within a single torch-spyre PR's repeated pushes?
  • What's the actual hit rate once keyed correctly — needs measurement before committing to the rework.
