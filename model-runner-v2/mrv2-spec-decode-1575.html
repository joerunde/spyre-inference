Speculative decoding (DFlash/XPress) on the V2 runner

Plan for #1575 (part of #906). vLLM v0.33.0, spyre-inference main at 4178907. Written before implementation, then self-reviewed (section 6).

In one paragraph. Upstream's MRV2 runner already drives a speculator through one seam. It builds self.speculator, loads it inside load_model, gives it attention groups in initialize_kv_cache, and calls propose(...) after every sampled step, then reads the result from req_states.draft_tokens. We keep all of that and replace only the speculator: one class, SpyreDFlashSpeculator(DFlashSpeculator). Its propose is V1's propose_spyre rewritten against MRV2's tensors, and its loader moves the draft to Spyre. The rest is removing five refusals and fixing three things they were hiding: aux-hidden-state wiring, lm_head row buckets and draft attention recording.

2. The speculator

New module spyre_inference/v1/worker/spyre/spec_decode.py: one file of about 150 lines, with one caller. It subclasses DFlashSpeculator for both draft architectures. Our draft model already handles both through propose_block (XPress refines when it has a head), so nothing in XPressSpeculator applies: its body is the Triton Jacobi refinement and the DSpark loader.

MethodBehaviour

propose, step by step

All bookkeeping is on the host: the runner's device is cpu, so num_rejected, last_sampled, input_batch.positions and the block tables are all CPU tensors. With at most 4 requests, plain loops are enough.

  1. Plan. A pure function, plan_drafts, unit-tested without a model. For each request i, valid = scheduled_i − num_rejected_i. This is exactly V1's accepted_context_length: num_rejected = drafts + 1 − sampled, and 0 for a chunked prefill. The first valid rows store context in the request's own pages; rejected and padded rows write the null page. A request drafts when num_sampled_i > 0 (it isn't a prefill chunk) and context_end + block ≤ max_model_len. Here context_end = positions[start+valid−1] + 1, and the anchor is last_sampled[idx_mapping[i]].
  2. Store context. combine_hidden_states(cat(aux)) → precompute_and_store_context_kv(context, positions, slots), at the target's padded row count. This runs every step, including steps where num_speculative_tokens == 0.
  3. Draft, if any request drafts and num_speculative_tokens != 0. Pad the active batch to a power of two. Each request gets block rows at positions context_end … context_end+K, with ids [anchor, mask×K] and slots from its block-table row. Build non-causal metadata through upstream's build_attn_metadata(self.attn_groups, ..., causal=False), run the forward, then call model.propose_block.
  4. Write the proposals into draft_tokens[i] for drafting rows, and zeros for the rest.
  5. Dummy run (warmup). Store context against the null page at this dummy's row count. Then, once per power-of-two batch, run a draft forward and propose_block, as V1's dummy_run does. Warmup already runs one dummy per body bucket, so every serving row count is covered.

No changes to kernels.py or the Triton gate, because our path launches no Triton. Upstream's rejection sampler and get_num_sampled_and_rejected do. On x86 they run on triton-cpu, like every other MRV2 kernel today, and they join DEFAULT_PATH_KERNELS with the rest when #1238 lands.
