MRV2 on Power and Z: patching the Triton kernels ourselves

Contingency for #1238 (part of #906) · 2026-10-28 · kernel counts from vLLM v0.32.0 (5df63a7203), upstream status as of vLLM main 9f0893f1ad. Estimates are from line counts and reading code; nothing here was measured on hardware.

TL;DR

  • What: keep subclassing upstream's GPUModelRunner as our MRV2 package does today, and replace each of its Triton kernels with our own through the existing kernels.py seam, so the runner works on ppc64le and s390x without Triton.
  • How: patch the kernel objects (module._foo_kernel = TorchKernel(impl)), not the wrapper functions. The wrappers look the kernel up as a module global on every call, so one assignment per kernel reaches every caller. A few pointer-table kernels are replaced one level up, as methods.
  • Nothing eager. Each replacement is either a C++ op in _spyre_C or compiled torch (torch.compile(dynamic=True, fullgraph=True), warmed at startup). Expected C++ set: the per-step metadata kernels (input batch, block table, slot mapping, staged writes) and Gumbel sampling. The vocabulary-sized feature kernels (penalties, min-p, logprobs, …) start as compiled torch and are ported only if a profile says so.
  • Size: 43 kernel launch sites across 38 wrapper functions outside spec decode. Nine run on every decode step, and two more on prefill steps or with a non-trivial temperature. The rest only run when a request uses a feature. Roughly 3–4 weeks to a working default path and 6–8 weeks to cover all features except spec decode, plus 0.5–2 days of upkeep per vLLM bump.
  • Build: no new toolchain. _spyre_C already builds with VSX and VXE flags in CI. The change is that it becomes mandatory for V2 on Power and Z. Today setup.py treats a failed build as a soft warning.

When to use this

Switch from the main plan to this one if both of these hold:

  1. We have to move to a vLLM release without V1. vllm#63373 ("Remove Model Runner V1", draft) lists "vLLM on CPU without Triton" among the features it drops, and the v0.29 release notes target v0.32 for V1's removal. We pin vllm>=0.31.0,<0.32.
  2. By then upstream has no merged non-Triton CPU runner that an OOT platform can use. That means one we can subclass or bind from even though our is_cpu() is False and we build vLLM without _C.

If upstream is close but not merged, prefer vendoring its pieces (exit path) over building ours from scratch. The mechanism below is the same either way. Only the implementation behind each binding changes.

How the patching works

Every MRV2 kernel launch has the shape _some_kernel[grid](tensor, stride, ..., BLOCK_SIZE=...) inside a wrapper function in the same module. The wrapper resolves _some_kernel as a module global each time it's called. Replacing the global reaches every caller of the wrapper, wherever it was imported by name:

# kernels.py
class TorchKernel:
    """Stands in for a @triton.jit object: kernel[grid](*args, **kw) -> impl(grid, *args, **kw)."""
    _LAUNCH_OPTIONS = ("num_warps", "num_stages", "num_ctas", "maxnreg")

    def __init__(self, impl):
        self._impl = impl

    def __getitem__(self, grid):
        def launch(*args, **kwargs):
            for opt in self._LAUNCH_OPTIONS:
                kwargs.pop(opt, None)
            return self._impl(grid, *args, **kwargs)
        return launch

def bind() -> set[str]:
    import vllm.v1.worker.gpu.input_batch as ib
    ib._post_update_kernel = TorchKernel(adapters.post_update)   # adapter calls torch.ops._spyre_C.mrv2_post_update
    ...
  • Why kernel objects and not wrappers: wrappers such as gumbel_sample, compute_topk_scores and the input_batch helpers are imported by name into model_runner.py, sample/sampler.py, sample/prompt_logprob.py and even model code (diffusion_gemma.py). Patching a wrapper means patching every importer, and a new importer after a bump would silently miss the patch.
  • The cost: each adapter is coupled to its kernel's argument list (pointers, strides, constexpr block sizes), which changes more often than wrapper names. The coverage test turns that into a failing test on bump.
  • Adapters stay thin. Each one drops strides and block sizes and calls a C++ op or a compiled function with a stable signature that we own, so a bump only touches the adapter.
  • Method-level exceptions: BlockTables.gather_block_tables / compute_slot_mappings (already stubbed in spyre/block_table.py), StagedWriteTensor.apply_write / FusedStagedWriter.apply, and MambaHybridModelState. Their kernels take arrays of device pointers that a torch or C++ op can't map back to tensors. #55847 makes the same split.

Prerequisites

  • Imports already work without Triton. Without Triton, vllm.triton_utils installs a placeholder whose @triton.jit returns the plain function. I checked every module-level use of tl.*/triton.* in worker/gpu/ outside spec decode, and all are covered by the placeholder. So the modules import, and only the kernel[grid] launches fail. One gap: triton.next_power_of_2 is called by wrappers before launch and isn't in the placeholder. bind() adds it, as #55847 does.
  • triton_gate.py (stubbed): get past VllmConfig.use_v2_model_runner's silent fallback to V1 and _validate_v2_model_runner's ValueError("Model Runner V2 requires Triton."). After #63373 the flag goes away. Recheck then that no top-level import triton appears.
  • device_shims.py (stubbed): torch.cuda Stream/Event placeholders. There are also about 44 pin-memory and UVA sites in buffer_utils.py, so we need a CPU UvaBufferPool. Use #60206 as the reference.

C++ or compiled torch

Rule: nothing runs eager. Eager torch on the step path is too slow. Each binding is either a C++ op in _spyre_C or a torch.compile(dynamic=True, fullgraph=True) function that warmup traces at startup, for every batch-size class it will see, so nothing compiles mid-serve. The size-1 batch dimension compiles separately, because dynamo specializes it.

  • Per-step metadata → C++. These kernels handle a few hundred integers per step. The arithmetic is trivial, and the cost is fixed overhead: dynamo guard checks, Python dispatch, and many small torch ops to express ragged gather and scatter. A plain C++ loop over requests is the natural fit and avoids all of that. #61995 has working versions to start from.
  • Gumbel → C++. It runs on every sampled token over the full vocabulary. We already ship fused_gumbel_argmax (splitmix64, vectorized for AVX512, VSX and VXE). MRV2 also needs per-row temperature, per-position seeding (seed, pos) and the is_drafting salt, so it's an extension of what we have, not a new kernel.
  • Vocab-sized optional features → compiled torch first. The work is large and regular, and inductor's CPU codegen handles it well. They run only for requests that ask for them, so they aren't on the default path's ITL.
  • Top-k/top-p is not a Triton kernel but still matters. MRV2 calls torch's apply_top_k_top_p, a full-vocabulary sort that our V1 SpyreTopKTopPSampler avoids. The main plan already flags this. It applies here too.

Build impact

Compared with today, there's no new toolchain or packaging. The CMake extension, the per-arch flags (-mcpu=power10 VSX, -march=z15 VXE, AVX512/AVX2), the cpu_types_*.hpp vector headers and the CI build_kernels job all exist for the V1 sampling kernels. What changes:

  • The build stops being optional for V2 on Power and Z. setup.py currently catches a failed CMake build, deletes the stale .so, and installs anyway with a warning, because V1's samplers have PyTorch fallbacks. For the MRV2 metadata kernels there is no acceptable fallback. kernels.bind_or_raise() must refuse to start V2 when a C++ op is missing, with a message pointing at the build log, rather than run slowly. V1 keeps today's soft behaviour until the flip.
  • The cost of a bug goes up. A sampling-kernel bug gives a slightly wrong token. The input-batch, block-table and staged-write kernels mutate persistent state (num_computed_tokens, block tables, slot mappings). A bug there corrupts later steps or writes KV into the wrong slots. That makes parity tests mandatory, on each architecture.
  • Three vector code paths. Only Gumbel and any vocab-sized op we port need SIMD. The metadata kernels should be scalar C++ and need no per-arch code. Keep SIMD to the ops a profile justifies.
  • Endianness: s390x is big-endian. None of these kernels reinterpret bytes except the RNG bit tricks and the grammar bitmask unpacking, which need an explicit test on Z.

Measuring before porting

The C++ set above is a prediction. What decides it is host time per step that the Spyre forward doesn't hide. We can measure that without cards:

  1. x86, vLLM's CPU backend with MRV2: run it three ways: triton-cpu (baseline), compiled torch replacements (vendored #55847 behind torch.compile), and eager. Use a small decoder and a large-vocabulary decoder at our max_num_seqs. torch.profiler one steady-state decode step, and rank kernels by host time.
  2. ppc64le and s390x: the same comparison between compiled torch and #61995's C++ through its generic vec.h path, since triton-cpu isn't available there.
  3. Threshold: port to C++ any kernel whose host time is a meaningful share of a Spyre decode step's ITL. A 50 µs kernel is noise next to a multi-millisecond step; 1 ms isn't. Once the cards are free, confirm on a Spyre ITL run against V1.

Tests

  • Parity against the real Triton kernel (tests/mrv2/kernels/): on x86 with triton-cpu, run upstream's wrapper with the Triton kernel and with our binding on randomized inputs, including ragged batches, empty batches, prefill/decode mixes, max blocks and padding, and compare outputs and every mutated buffer. CPU only, no cards, no model load.
  • The same parity tests on ppc64le and s390x against stored reference outputs generated on x86, since Triton can't run there. This catches VSX/VXE and endianness bugs.
  • Coverage (tests/mrv2/test_kernel_coverage.py, already planned): walk the installed vLLM's worker/gpu/ for kernel[grid] launch sites, and fail if any isn't bound or in an explicit skip list. Also fail if an adapter's parameter list no longer matches the kernel's signature. This is what makes a vLLM bump fail loudly instead of mid-serve.
  • Seeded sampling: the same seed and position give the same token across preemption and resume, and across TP ranks.
  • End to end: the existing bring-up runs, repeated on Power and Z hosts.

Risks

  • #63373 may make Triton structural. If removing V1 also brings a top-level import triton or Triton-only module state into worker/gpu/, the placeholder trick stops working and the patching needs import hooks. Watch the diff.
  • We'd be duplicating upstream. #61995's C++ covers most of K2. Vendoring it, with the source SHA in each header as _vendored/ already prescribes, is cheaper than writing our own, licence permitting (Apache-2.0 both sides).
  • Divergence from the eventual upstream runner. If upstream ships a separate CPU MRv2, its components won't match GPUModelRunner's, and moving to it is a runner change, not a kernel swap. See exit path.
  • Signature churn. Kernel arguments change more often than wrapper names, at about 50 commits a month to worker/gpu/. The coverage test makes it visible but doesn't make it free.
  • Seed semantics. Our V1 sampler, #55847 and upstream's GPU kernel don't all use the same RNG. See decision 2.

Decisions needed

  1. Trigger date. Which vLLM bump forces the choice: the one that removes V1, or earlier?
  2. RNG. Port upstream's murmur3 (as #61995 does) so seeded requests match GPU vLLM, or keep our splitmix64 so they match our V1 runner? Matching upstream is easier to defend and to test against triton-cpu.
  3. Vendor or write. Start K2 from #61995's C++ (vendored, then adapted to our ops and arches), or write our own against the kernel semantics?
  4. Unsupported features. Which K5 features we reject at request validation rather than implement.

Exit path

Every binding goes through kernels.py, so whichever way upstream moves, unwinding this is local:

  • Upstream ships non-Triton kernels usable from an OOT platform: point bind() at them, delete ours, keep the parity and coverage tests. That's the main plan's step 2.
  • Upstream ships a separate CPU MRv2 (the Slack outcome): re-base SpyreModelRunnerV2 on it. Our C++ ops become candidates to upstream into it, and the adapters go away.
