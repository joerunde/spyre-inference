Two ways to run Model Runner V2 without Triton on Spyre

Both spikes run Spyre's V2 runner on x86 with Triton uninstalled, and both match V1 token-for-token on the decoder path. They differ in one layer: what sits under SpyreRunnerMixin, and where the per-step host kernels come from.

Choose A when

We need to ship V2 on Power/Z before #61995 lands

  • Works on the vLLM we pin today, with every model state the bring-up supports.
  • Every kernel is checked against triton-cpu on x86, so a Power/Z port has a reference.
  • The cost is ours to keep: kernel signatures churn monthly, and we own the C++.
Choose B when

#61995 merges on a release torch-spyre can run

  • Upstream owns the kernels and the runner; our layer is the mixin and one override.
  • Until then it rides on an 8k-line backport and covers decoders only.
  • Top-k/top-p trailing V1 by 6–8% on the 1B model wants a profile before it ships.

They compose. The Spyre layer is the same code in both, now a mixin on B's branch. A's parity suite can check B's ops too, since it compares upstream wrappers against triton-cpu, and A's bind() is already the place to point at upstream kernels once they exist. A practical order: ship A as the hedge now, and move to B's base when #61995 is on a release we pin.

Not compared yet: B on gemma-4, and either approach on Power or Z hardware. A's numbers are from this host at TP2 (2 cards); B's are one run each on the 1B model.

Part 2 · added 2026-10-30

Who owns the kernels, and how fast can each side move

Both runners work today. The choice is about who carries the host kernels from here on. Under A they live in our repo and we can change them whenever we like, but every vLLM bump can break them. Under B they live in vLLM and keep working across bumps, but any change to them waits on vLLM's review and its release train.

A We own it

Lives in
spyre-inference/csrc/cpu/mrv2_kernels.cpp plus kernels.py's bindings.
Consumed by
Overwriting 46 module-level kernel objects in vLLM's GPU runner at worker start. vLLM never knows we're there.
We can change
Anything, any day: Spyre-specific shapes, faster SIMD paths, a dtype vLLM doesn't use. The vectorised Gumbel and logprob kernels landed in one afternoon.
Breaks when
vLLM adds, renames or re-signs a Triton kernel. Nothing upstream warns us; our coverage test fails at the bump.
Per-bump cost
Re-run coverage and parity, then port the changed kernels. Most changes are new arguments for features we reject, so the port is small but never zero.

B vLLM owns it

Lives in
vLLM: vllm/v1/worker/cpu/ and its csrc/cpu host kernels, today only on a backport branch until #61995 merges.
Consumed by
Subclassing NoTritonCPUModelRunner and calling its ops as any CPU user does. One override on our side, for bucket padding.
We can change
Only through an upstream PR: a reviewer has to agree it belongs in vLLM, and it ships in the next release. Spyre-only tweaks are a hard sell.
Breaks when
The CPU runner's own API changes. That's a public surface with other users, so changes come with notice and usually a migration.
Per-bump cost
A version bump. Kernel churn is upstream's problem, fixed before release by the people changing the GPU kernels.

Read together. A trades a steady tax for freedom: about a day or two per release, roughly every two weeks, in exchange for being able to fix or tune a kernel the same day. B trades freedom for a smaller tax: bumps are close to free, but every kernel change becomes a negotiation with a two-week shipping floor. B also can't start until #61995 merges on a vLLM whose torch torch-spyre supports; until then B means carrying an 8k-line backport, which costs more per bump than A does.

Estimates: the 1–2 day figure is from the size of the 0.31 → 0.32 diff above, not from doing that port. The 2–6 week figure is one review cycle plus a wait of zero to two release cuts; #61995 itself has been open since 2026-10-16.
