Model Runner V2 migration, in pictures

Companion to the MRV2 investigation report for spyre-inference#906 · 2026-10-09 · each comparison puts today (V1) on the left and the proposal (V2) on the right, in the same layout.
Starting point: vLLM v0.31.0 with #945 landed, so the V1 panels show the runner after that bump.

The 60-second version

vLLM's model runner is the component that, every step, turns the scheduler's decision ("run these requests, this many tokens each") into tensors, calls the model, samples the next tokens, and keeps per-request state. It also loads the model and sets up the KV cache at startup. Our Spyre plugin customises the runner heavily: shape bucketing so compiled graphs are reused, a paged KV cache laid out for Spyre, attention metadata, pooling, and a boundary that keeps integer bookkeeping on the host CPU and only sends model inputs to the card.

Today we do that by subclassing vLLM's V1 runner and overriding its private methods. vLLM has replaced it with Model Runner V2 (MRV2) and plans to delete V1 (target: v0.32). MRV2 suits us better structurally (public seams instead of private overrides), but it assumes a GPU: about 20 of its per-step operations are Triton kernels, which Spyre does not have. We supply pure-torch replacements, ideally shared upstream with vLLM's Power, Z and Arm CPU backends, which need the same thing.

The four parts answer: how the code fits together (1), what changes at model load (2), what changes on every inference step (3), and what it means for KV-cache management and batching (4).

1 · How the code pieces fit together

1a · Component map: what we subclass, own and replace

Context
A vLLM platform plugin like ours supplies a worker (owns the device) and a model runner (turns scheduler decisions into model calls). Today our runner subclasses V1's monolithic GPUModelRunner and overrides its private methods. MRV2's runner is a thin, model-agnostic loop that owns replaceable helper objects.

  • Fewer, public overrides means smaller diffs on each vLLM bump, but MRV2 itself still changes a lot between releases (roughly 3–6k lines per release in its directory), so the bump tax shrinks rather than disappears.
Details: seam map · strategies · A1

1b · Hook rewiring map: where each override goes

Context
Today our runner customises vLLM by overriding private methods of the V1 GPUModelRunner (left). MRV2 deliberately keeps its runner model-agnostic and pushes behaviour into small helper objects (ModelState, PoolingRunner, the CUDA-graph manager, BlockTables, Sampler). So the port is mostly re-homing existing Spyre logic onto public, typed seams (right), not rewriting it.

  • Five overrides fail silently, so the port needs an explicit checklist and tests for them (window split, bucket padding, force_attention, the spec-decode guard, pooling output).
  • Three objects are brand new helpers we own (SpyreModelStateMixin, SpyrePoolingRunner, SpyreBucketManager); two more replace upstream kernels (SpyreBlockTables, SpyreSampler).
Details: seam map · dead-override checklist · A2 · A3

1c · Where tensors live (host vs. Spyre)

Context
Spyre has no native int32 and no indexing ops, so all of the runner's integer bookkeeping stays on the host CPU and only model inputs cross to the card. MRV2 allocates every buffer on the runner's device; we keep that set to CPU, exactly like vLLM's own CPU MRV2 runner.

Details: multimodal · input prep · A6 §2.9

2 · Model-load sequence

2 · Model-load sequence

Context
Before serving, vLLM asks the platform to configure itself, the worker to grab the device, and the runner to load weights, size and allocate the KV cache, and warm up. Warmup matters a lot on Spyre: every shape the server will ever run is compiled here, then compile_guard is armed so any later compile is flagged.

  • V1 lets us hook KV setup at two separate points; MRV2 does it in one monolithic method we override wholesale.
  • The kernel-registration step is new: today #945 swaps a single slot-mapping kernel; MRV2 needs about 20 torch kernels registered before the worker is built.

3 · Inference-time sequence

3a · One inference step: who runs what

Context
Every engine step the runner turns the scheduler's decision (which requests, how many tokens each) into tensors, runs the model, samples a token per request and updates its own per-request state. Rows are those phases, in call order; columns say whose code runs and where. The purple column is the Spyre card; every purple arrow is a host↔device copy.

  • The Spyre-specific logic (bucket padding, encoder plan, grid expansion, row-bucketed logits) survives intact; only the object that hosts it changes.
  • The new work is the gear count: input prep, block tables, sampling and post-update all become kernels we own (and can share upstream with vllm#55847).
  • Async output keeps its shape, but its CUDA events become placeholders (pooling needs a real Spyre sync, see 3c).
Details: input prep · kernel inventory · A3 · A6

3b · Where the next token comes from

Context
During decode, the token sampled in step n is the input of step n+1. The scheduler is not in this loop in either runner: the runner keeps the token itself. What changes is who writes and reads it.

  • This is the top correctness risk of the port: an off-by-one in either replacement kernel silently feeds the wrong token, so they need exact unit tests against the Triton reference and token-exact greedy e2e checks.
Details: input prep · A6 §2.1, §2.4

3c · Pooling step (embedding / rerank models)

Context
Pooling models (embeddings, rerankers, ~12 in our test suite) return one vector per request instead of sampling tokens. On Spyre we pool on the card and copy back only the pooled rows, because slicing a Spyre tensor along dim 0 and non-blocking D2H copies are not safe there.

  • This is the only per-step override that is a genuine redesign rather than a move (counted as 1 of 21 in A3).
Details: pooling · A7 §4

4 · KV cache management and runtime batching

4a · Paged KV cache anatomy (shared by both runners)

Context
vLLM stores attention keys and values in fixed-size pages (blocks). Each request owns a list of blocks (its block-table row), so memory is allocated incrementally and freed without fragmentation. The slot mapping tells the attention layer exactly where each new token's K/V is written. None of this changes conceptually in MRV2; what changes is who computes the tables (4b). Allocation stays ours: one K/V pair per layer, as #945 does on V1, moved into MRV2's initialize_kv_cache override.

Details: attention & KV · A5

4b · Who owns block tables and request rows

Context
The runner keeps per-request state across steps (token ids, how many tokens are already in the KV cache, block-table row). V1 keeps it in a persistent batch whose rows are the batch; MRV2 gives each request a stable slot and builds a fresh batch-ordered view every step.

  • Simpler invariants (no condense/swap), at the cost of a gather per step, which we keep vectorised on CPU.
Details: attention & KV · A5 §3 · A6 §2.1-2.4

4c · Batch formation and padding

Context
Each step, the requests' new tokens are flattened into one token batch. Spyre compiles one graph per shape, so we pad the batch up to a small set of warmed sizes (“buckets”) instead of compiling for every length. The slot mapping tells the attention layer where each token's K/V goes in the paged cache; padding tokens get slot −1.

  • The bucket manager is about 40 lines but is the single most important piece for keeping compile counts flat; compile_guard will flag it immediately if it regresses.
Details: bucketing · A6 §2.5, §2.7 · A8 §0.4

4d · Warmup dummy batches

Context
Warmup runs fake “dummy” batches at every bucket size so all shapes are compiled before serving. In V1 these dummies skip attention entirely and we pre-record attention kernels in a separate, controlled pass. MRV2 changed the dummy run to always build attention metadata.

Details: warmup measurements · A5 §9 · A8 §2.2
