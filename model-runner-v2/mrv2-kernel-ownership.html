Who owns the MRV2 host kernels: three options

Model Runner V2 drives every step through small host kernels: input preparation, block tables, sampling and rejection sampling. Upstream writes them in Triton, which Spyre's hosts can't run. Something has to replace them, and the choice that matters for upkeep is where the replacements live and whose release train they ride. This page lays out the three placements, what each one costs per vLLM bump and per kernel change, and what we propose to do in which release.

This expands Part 2 of No-Triton spikes compared, which compared two of these options. The architecture and correctness of the spikes are covered there and not repeated here.

Proposal

  1. Start with A, on vLLM 0.33.0. It is the only option that runs on 0.33: vllm#61995, the Triton-free CPU runner that B and C build on, merged on 2026-10-30, after 0.33 was cut. 0.34 is expected to remove Model Runner V1 (vllm#63373, on the Q4 roadmap), and our V1 runner subclasses and imports from the V1 files it deletes. To be able to bump past 0.33 at all, MRV2 has to be tested and working on 0.33.
  2. From 0.34.0 on, reconsider B or C, once the CPU runner is on a release we can pin. The deciding question is spec decoding. The upstream CPU runner doesn't support it, and we need it on V2.
  3. Assume that we maintain the CPU runner's Spyre-relevant features ourselves under B or C, spec decoding first. The CPU runner is a hand-ported copy of the GPU runner, and it trails the GPU runner on every feature. Nobody upstream is assigned to port the features we need.

The three options

A · subclass the GPU runner, we own the kernels

Keep upstream's GPUModelRunner as the base. At worker start, kernels.bind() overwrites each Triton kernel global in vllm/v1/worker/gpu/ with a host op from our _spyre_C extension, using the same argument list.

Spike: mrv2-kernel-patching, which has 34 host ops and 12 named stubs. Spec decode isn't covered yet.

B · subclass the CPU runner, vendor its kernels

Base on upstream's Triton-free CPU runner (StandaloneCPUModelRunner in vllm/v1/worker/cpu/, called NoTritonCPUModelRunner before it merged). Copy its C++ kernels from vLLM's csrc/cpu into ours with the source SHA, and edit our copy where Spyre needs something different.

Spike: mrv2-no-triton-032, which already does this (block table, input batch and sampling C++). On V1 we already vendor four rejection-sampling kernels this way (csrc/cpu/spec_decode_utils.cpp).

C · subclass the CPU runner, vLLM owns the kernels

Same base as B, but the kernels come from vLLM's own _C extension and we carry none. Our layer is the Spyre mixin plus the prepare_inputs padding override. Any kernel change goes through an upstream PR.

No spike. This requires us to build vLLM with its CPU extension, not with VLLM_TARGET_DEVICE=empty as we do today.

The snag: spec decoding, and a CPU runner that trails the GPU runner

Spec decoding is the feature that keeps us on A after 0.34. On V1 we already run XPress speculation (#1394, #1436). On V2 we need the same feature, and the upstream CPU runner doesn't have it:

  • StandaloneCPUModelRunner on vLLM main raises NotImplementedError("CPU Model Runner V2 without Triton supports one sampled token per decode step."), and get_draft_model() returns None.
  • #61995's description lists speculative decoding as unsupported and says it was left out to keep the PR small: "we can either add later or hopefully we won't need to if we pull-off triton-cpu fast enough." The CPU maintainers may decide to wait for triton-cpu instead of porting spec decoding. That doesn't help us, because triton-cpu covers only x86, and we need Power and Z.
  • The work is more than kernels. Upstream's XPressSpeculator subclasses DFlashSpeculator, and that class imports the GPU runner's InputBatch, BlockTables and ModelState. The CPU runner has its own parallel copies of those classes. Porting spec decoding to B or C means porting this wiring and the kernels it launches. On 0.33 that is 13 kernels: rejection sampling (8), DFlash input preparation (1) and the XPress refinement kernels (4).

The broader problem is how the CPU runner is built. It is a separate 1.3k-line copy of the GPU runner's step, maintained by hand. Every MRV2 feature lands in vllm/v1/worker/gpu first and reaches the CPU runner only if someone ports it. In the 30 days before this draft, worker/gpu saw at least 100 commits (56 in spec_decode/ alone), while worker/cpu saw 2, one of them #61995 itself. The CPU maintainers port what their own users need. For anything else Spyre depends on (spec decoding, the speculators we use, model states the CPU runner hasn't ported), the porter will be us.

What this means for B and C. Under both, we become co-maintainers of vllm/v1/worker/cpu for the features we use. B lets us carry a port in our tree while it is under review. C requires the port to be merged and released before we can use it. If we don't do this work, B and C get spec decoding only when the CPU maintainers want it, and that may never happen.

When each option is available

vLLM 0.33.0 · released 2026-11-02

A runs. B only on the 8.1k-line backport. C not possible.

V1 is still present, and this is the last release where we can run V1 and V2 side by side for parity. Testing MRV2 has to happen here.

vLLM 0.34.0 · ~mid-November (estimate)

A keeps running. B becomes possible without the backport. C becomes possible if the _C build works for us.

If #63373 lands, V1 is gone, and our V1 runner (which subclasses gpu_model_runner.GPUModelRunner and imports from cpu_model_runner) stops importing.

0.34.0 and later · re-evaluate

Move to B or C when the criteria below hold. Until then, stay on A.

What would make us switch

A → B when

  • The CPU runner is on a release we pin (0.34 or later).
  • Spec decoding works on a CPU-runner subclass, whether upstream wrote it or we did, and we have someone to keep it current as spec_decode/ moves.
  • B matches A on the gemma-4 shapes. The previous page measured only the 1B model under B, and top-k/top-p trailed V1 by 6–8%.
  • A's per-bump cost, measured on the 0.33 and 0.34 bumps, is clearly higher than B's re-vendoring cost would be.

B → C when

  • Every edit we carry in the vendored copy has been upstreamed.
  • vLLM's CPU kernels load without coupling us to vLLM's torch pin, either because torch-spyre tracks the same torch or because upstream offers a _C-free path (already one of our asks, #1238).
  • Spec decoding is merged upstream in the CPU runner.
  • We can accept a 2–6 week wait on any kernel fix.

Stay on A if

  • Spec decoding in the CPU runner has no owner, upstream or here.
  • We need Spyre-specific kernel changes (shapes, dtypes, SIMD paths) faster than vLLM releases.
  • The CPU runner falls behind the GPU runner on a model state we ship.

Read together. A is the only option that meets the 0.33 deadline. It also keeps spec decoding on the GPU runner's wiring, where upstream does the porting work. It costs a per-bump tax that rises once spec decoding is in scope. B moves the seam to a public class and keeps the kernels under our control. In exchange, we have to port and maintain whatever the CPU runner lacks, starting with spec decoding. C costs the least per bump, but only once the CPU runner already has everything we need and we can build vLLM's _C. It also hands every kernel change to vLLM's review process. The options build on each other: A's parity suite can check B's vendored ops, and the Spyre mixin is the same code under all three. So the realistic path is A now, and B or C when the criteria above hold.
