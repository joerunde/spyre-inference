Model Runner V2: implementation plan

Follow-on to the investigation report for #906. The report covers what an MRV2 runner needs; this page covers how we build it. · 2026-10-09 · against spyre-inference ad76a00 (main pins vLLM v0.28.0; #945 to v0.31.0 is still open).

TL;DR

  • Build it beside V1. All new code goes in a new package, spyre_inference/v1/worker/spyre/, next to the flat V1 files as upstream does with gpu/. The package is MRV2-only, and its docstrings say so (naming). No V1 module imports it. Importing it has no side effects. The platform still picks TorchSpyreWorker. V1 files are not edited until the flip PR, with one small exception in the bring-up phase.
  • Small files, one job each. About 25 files that mirror upstream's vllm/v1/worker/gpu/ layout, each aiming for 300 lines or fewer. That's a guideline for review, not a hard limit. model_runner.py stays a thin coordinator that hands each concern to a component module.
  • Kernels come from upstream. MRV2's step path, the sampler included, runs Triton kernels, and their non-Triton replacements don't exist upstream yet (an Arm CPU maintainer announced a PR on the vllm#55847 thread, 2026-10-09). So: use the Triton kernels on x86 through triton-cpu in the meantime, swap to upstream's replacements as-is once they exist, then measure them on Power and Z before deciding whether to improve them here or upstream (kernel strategy). All binding goes through one module, kernels.py. Two risks to raise upstream now: we build vLLM with VLLM_TARGET_DEVICE=empty, so there is no _C, and our platform is OOT, so is_cpu() is False.
  • Small CI cost. New tests live in tests/mrv2/. They're mostly light CPU checks with fakes, plus a few very light, fast hardware tests that skip on CPU hosts. A conftest guard fails any test that loads a model or calls torch.compile. The whole directory should finish in about 20 s. We also test what we can on hardware by hand, with overrides. Full CI coverage arrives with the flip PR, when the existing suites run on V2. We don't parametrize the suites over v1|v2, because that would double CI.
  • Four waves. Wave 0 is one serial skeleton PR that fixes the files, class stubs and interfaces. Wave 1 is nine work packages that run in parallel, each owning its own files and tests. Wave 2 is end-to-end bring-up on hardware. Wave 3 is the flip.

Ground rules

Each of the five constraints becomes a rule we can check in review or with a test.

1 · Don't disrupt existing work

  • New code only goes under spyre_inference/v1/worker/spyre/ and tests/mrv2/.
  • Nothing outside spyre/ imports it. A test walks the AST of every module in spyre_inference/ and checks this.
  • Importing the package does nothing. The torch.cuda placeholders, the Triton-gate patch and the kernel registration run only from the V2 worker's init_device.
  • The only dependency change is triton-cpu as an x86-only entry in pyproject.toml and uv.lock (kernel step 1). Power and Z resolve exactly as today, and V1 keeps Triton off on x86.
  • If a shared helper doesn't fit, we subclass or wrap it inside spyre/ and leave the original alone. Each case goes on the move-at-flip list.

2 · Don't blow up CI time

  • Tests use hand-built fakes, with no LLM(...), no HF downloads and no subprocess engine. Most run on CPU.
  • A few light hardware tests are allowed: tiny tensors, eager ops only, skipped by spyre_available() on CPU hosts.
  • An autouse fixture in tests/mrv2/conftest.py makes torch.compile and vllm.LLM.__init__ raise.
  • Budget: under 1 s per test and about 20 s for the directory. A session-finish hook fails the run when the total goes over.
  • These tests are unmarked, so they run in the smoke shards, which run them anyway.

3 · Plan for parallel work

  • Wave 0 writes every file, with real signatures and NotImplementedError bodies.
  • Each Wave 1 package owns a disjoint set of files: its source files and its test files.
  • model_runner.py, worker.py and the shared fakes belong to Wave 0 and Wave 2, not to Wave 1 packages.
  • Wave 1 packages are independent, so any number of agents can work on them at once.

4 · Get the encapsulation right

  • The layout mirrors upstream gpu/: every Spyre file maps to the upstream file it extends.
  • Files aim for 300 lines or fewer. Reviewers flag a file that grows past that and ask whether it holds two jobs. There's no hard limit and no test for it.
  • Per-step encoder state moves off the runner and onto the model state, where MRV2 expects it.
  • Imports point one way: components → shared Spyre modules → vLLM. Components never import model_runner.py.

5 · Kernels come from upstream

  • All kernel binding goes through one module, spyre/kernels.py.
  • Triton kernels through triton-cpu on x86 while we wait, shipped as an x86-only locked dependency. Upstream's replacements as-is once they exist. Our own changes only after measuring on Power and Z.
  • A coverage test lists every default-path @triton.jit kernel and fails when one of them has no binding.

Keeping #945's rebase cheap

Every tests/mrv2 test that lands before #945 is one more test #945 has to keep green when it rebases. Two rules keep that small:

  • Before 0.31, don't touch the seams that changed (the KV schema, get_mm_embeddings, load_model internals, the sampler). The table above lists them.
  • Before merging any pre-0.31 mrv2 PR, also run uv run pytest tests/mrv2 on a checkout of the #945 branch. It's CPU-only and takes seconds. If it fails there, fix the PR first so #945 doesn't inherit the problem.

Order

  1. Now, on 0.28: WP0 (including worker.py), then in parallel WP-B, WP-D (minus the embeds hook), WP-F, the attn_groups.py/block_table.py half of WP-C, the shims, gate and x86-only triton-cpu dependency from WP-A, and warmup.plan() from WP-H.
  2. After #945 lands: kv_cache.py, WP-E, WP-G, WP-I, kernels.py, warmup.run().
  3. After 0.32: WP-G's compile suppression and the compiled steps of Wave 2 bring-up.

Making "MRV2 only" obvious

Upstream's gpu/ doesn't say "V2" either, and readers mix it up with gpu_model_runner.py all the time. Until the flip, v1/worker/spyre/ sits next to spyre_model_runner.py, so the code has to make the split obvious:

  • The package docstring (spyre/__init__.py) says what the package is, what it isn't, and where V1 lives: 
    """Spyre Model Runner V2 (MRV2) implementation. MRV2 ONLY.

Subclasses vLLM's MRV2 runner and its components (vllm/v1/worker/gpu/).
Nothing here is used by the V1 runner, and no module outside this package
imports it. The V1 runner is spyre_model_runner.py / spyre_worker.py, next
to this package; those files are deleted when V2 becomes the default (#906).
"""
  • Every module's docstring starts with MRV2: and names the upstream class or file it extends: 
    """MRV2: Spyre bucket padding via ModelCudaGraphManager.dispatch (gpu/cudagraph_utils.py)."""
    test_layout.py checks both rules, so a module without the marker fails CI.
  • Class names carry the suffix: SpyreModelRunnerV2 and SpyreWorkerV2, so a traceback or a --worker-cls value says V2 even when the path doesn't. Component classes (SpyreBucketManager, SpyrePoolingRunner, ...) take their names from the upstream MRV2 class they extend, which only exists in MRV2.
  • Imports from V1 are labelled: each place that imports a V1 module-level helper (_SpyreModelWrapper, the compile helpers) gets a one-line # shared with V1; moves at the flip comment, which doubles as the move-at-flip list.
  • The startup log line says it: SpyreWorkerV2.init_device logs Using Spyre Model Runner V2, so a run's log shows which runner it used.
  • CLAUDE.md: WP0 adds a line under "Key modules" that says v1/worker/spyre/ is MRV2-only and isn't wired up yet, so agents working on V1 leave it alone.

What model_runner.py looks like

Wave 0 writes this in full. Wave 1 packages fill in the modules it calls and leave it alone.

class SpyreModelRunnerV2(GPUModelRunner):
    def __init__(self, vllm_config, device):
        super().__init__(vllm_config, torch.device("cpu"))
        self.spyre_device = device

    def load_model(self, *args, **kwargs):
        load.load_and_wrap(self, *args, **kwargs)        # load.py, compile.py

    def initialize_kv_cache(self, kv_cache_config, **kwargs):
        attn_groups.init(self, kv_cache_config)          # attn_groups.py
        kv_cache.init(self, kv_cache_config, **kwargs)   # kv_cache.py, block_table.py
        self.cudagraph_manager = bucketing.SpyreBucketManager.from_runner(self)

    def pool(self, *args, **kwargs):
        return pool_output.pool_sync(self, *args, **kwargs)  # pool/output.py

    def warming_up_model(self):
        warmup.run(self)                                 # warmup.py

Reuse vs. V2-local

Everything below the runner is shared with V1: attention, custom ops, bucketers, compile guard and the pooler heads. The V2 package imports these modules as they are. It doesn't copy them, and it doesn't refactor them before the flip.

A V2 module importing private names from spyre_model_runner.py is the one deliberate coupling. It's acceptable because V1 never changes because of it, and the flip PR moves those helpers to a shared module (v1/worker/model_wrapper.py, v1/worker/block_compile.py) with git mv. Doing that move now would conflict with every open PR that touches the runner.

Kernel strategy

What we know today:

  • MRV2 launches about 20 Triton kernels on its default step path: input preparation, block tables, staged writes, and the sampler. Every sampled token goes through the Triton gumbel_sample, greedy included.
  • Non-Triton replacements don't exist upstream yet. On the vllm#55847 thread, fadara01 (Arm) said on 2026-10-09 that they are "preparing a PR to migrate all non triton CPU backends to MRv2, including Arm, RiscV, ppc64le, etc.", with C++ where the torch version is too slow, and will ping us to test on IBM hardware. The open #55847 torch fallbacks are, by their author, superseded on x86 by #58140, which installs prebuilt triton-cpu wheels.
  • Our V1 runner samples on the host with copies of vLLM's V1 CPU sampling kernels (fused_gumbel_argmax, greedy_argmax), compiled into _spyre_C by #1111. Upstream only calls them when is_cpu() is true, which it isn't for our platform. They're today's performance baseline.

The plan follows those facts in three steps, all through kernels.py:

  1. Use the Triton kernels on x86 while we wait. Ship triton-cpu as an x86-only dependency in pyproject.toml and the lock, the way vLLM's requirements/cpu.txt does (the triton-cpu v3.8.0 wheel, marked platform_machine == "x86_64"). Today's "triton; sys_platform == 'never'" override becomes an x86-only entry for that wheel, so Power and Z resolve exactly as they do now. Then every x86 checkout can run the V2 runner while it's being developed, and tests/mrv2 can exercise real MRV2 components on x86 runners, skipping where Triton is absent.
    • V1 on x86 stays Triton-free. vLLM's HAS_TRITON check (triton_utils/importing.py) only accepts Triton's CPU backend when the vLLM version string contains cpu, which ours doesn't. It then finds no active non-CPU driver and sets HAS_TRITON = False. The exception is when CUDA_VISIBLE_DEVICES is set but empty: then it leaves Triton on. The PR that adds the dependency checks for this, and the existing x86 CI has to stay green with triton-cpu installed.
    • triton_gate.py turns Triton on for the V2 path only. It overrides that check from SpyreWorkerV2.init_device and the bring-up switch, and nothing else changes it.
    • Land it as its own small PR. It touches pyproject.toml and uv.lock, which #945 also touches, so whichever lands second regenerates the lock. Don't cherry-pick it to release-0.5.
    MRV2's kernels run unmodified, so x86 development and bring-up exercise exactly upstream's behaviour. Power and Z can't run MRV2 until step 2.
  2. Swap to upstream's replacements as-is once they exist. However they arrive: registered by upstream once they reach our pin (registering them ourselves if they're keyed on is_cpu()), copied verbatim into spyre/_vendored/ with the source SHA if we need them before our pin has them, or compiled into _spyre_C if they're C++ in vLLM's _C, as #1111 did for the V1 sampling kernels. The sampler comes with them, so we also take MRV2's sampling semantics, including its per-position seeding (decision 3).
  3. Measure on Power and Z, then decide. Compare per-step host time for input preparation and sampling against today's V1 runner on the same models: a large-vocabulary decoder at max batch, and a pooling model. If the replacements are slow there, either (a) plug in our own improvements through kernels.py or a component subclass, or (b) contribute the improvements upstream. Prefer (b); take (a) when the need is Spyre-specific or upstream's timing doesn't fit ours.

Raise these on the upstream PR now, before it's written around our blind spots:

  • No _C. We build vLLM with VLLM_TARGET_DEVICE=empty. A pure-torch path that stays registered when _C is missing saves us from compiling upstream's C++ into _spyre_C.
  • Gate on capability, not on is_cpu(). Our _enum is OOT. If the fallbacks or the Triton-gate exemption are keyed on current_platform.is_cpu(), we're shut out. Ask for a platform capability (as #57684 asks), or make the registration reusable from an OOT platform.
  • s390x is big-endian. Offer Z hardware for testing, along with ppc64le.
  • Scope. We also need the sampler kernels (gumbel/temperature, logprobs, penalties, min_p, bias, bad_words), not only input prep. Check they're included.

The coverage test (tests/mrv2/test_kernel_coverage.py) imports the MRV2 modules, lists every @triton.jit on the default path and fails when kernels.py has no binding for one. It's a pure import-and-inspect test, and it's what catches a renamed kernel after a bump.

Hardware during Wave 1

The CPU tests check each component's logic. With triton-cpu in the x86 lock, the whole V2 runner also runs on x86 Spyre hosts, so for the parts whose behaviour depends on the device we use two lighter tools until the flip:

  • Manual testing with overrides. Run a component, or the whole V2 worker, on a Spyre host by hand. The overrides are --worker-cls spyre_inference.v1.worker.spyre.worker.SpyreWorkerV2, VLLM_USE_V2_MODEL_RUNNER=1, and triton_gate.enable() applied locally until the WP-INT switch lands. Note what was checked in the PR description.
  • Very light, fast hardware tests. A WP may add one or two tests that skip with spyre_available() on CPU hosts. Each one uses tiny tensors and eager ops only, with no compile and no model, and finishes in about a second.

Deferred to the flip PR

End-to-end, attention, pooling, distributed, quality and upstream tests all start exercising V2 the moment the flip PR swaps the default worker. That's where token-exact greedy and pooling cosine comparisons against the existing references happen. Seeded sampling output changes, because MRV2 seeds per position (decision 3). Our local references are all greedy (temperature=0), so none need regenerating. Interfaces WP0 has to settle

These are the only cross-package contracts. If they're right in WP0, Wave 1 packages never need to edit each other's files.

  • bucketing.SpyreBucketManager.from_runner(runner) and .bucket(num_tokens) -> int. Warmup enumerates through this.
  • encoder_plan.EncoderPlan: a dataclass for the per-step plan (rectangle/ragged, grid, rows), set by WP-D, read by WP-F and WP-H.
  • kv_cache.init(runner, cfg, **kw) and attn_groups.init(runner, cfg), plus the attribute names they set on the runner (attn_groups, kv_caches).
  • load.load_and_wrap(runner): postcondition is that runner.model is the wrapper and every holder points at it.
  • kernels.bind() -> set[str] and DEFAULT_PATH_KERNELS.
  • warmup.plan(runner) -> list[DummyCall] kept apart from warmup.run(runner), so the plan can be tested without running anything.

Warmup policy

Decided by the report's warmup measurements (x86 Spyre host, granite-3.3-8b, TP1): decoder dummies skip attention. The report calls this warmup option B. It's what V1 does today: 724 s for a cold warmup. The alternatives measured worse:

  • MRV2's default dummies (attention on): +62 s (+8.6%), from 7 extra attention compiles whose metadata differs from what the recorder builds.
  • One request per dummy: +7 s, but it under-warms the sampler. The logits have one row, so 5 sampler widths go unwarmed and compile on the first real batch, after compile_guard is armed.

How warmup.py implements it on MRV2:

  • Decoder dummies call _dummy_run(N, skip_attn=True, is_profile=True). MRV2 only allows skip_attn together with is_profile.
  • Pooling dummies keep attention on, as V1 does with force_attention.
  • Attention recording stays a separate pass over attn_groups, followed by the sampler dummy sized from the dummy's logits.

What is_profile=True also does (v0.31 model_runner.py, dp_utils.py): it sets need_eager, so dispatch_cg_and_sync_dp skips cudagraph_manager.dispatch() altogether. That means SpyreBucketManager never sees a warmup dummy. It also builds the dummy batch with is_padding=False. So warmup.plan() has to pick already-bucketed num_tokens, and set num_reqs = min(N, max_num_seqs) itself, and the plan test checks both. Upstream ask: a warmup flag that skips attention without implying is_profile, so that dummies go back through dispatch().

The same measurements show that attention recording is 64% of a cold warmup, and that attention kernels miss the persistent kernel cache across restarts. Fixing that saves far more than any dummy-run choice. It doesn't depend on MRV2 and is tracked in the report, not here.

Wave 1's nine packages fall into five issues (2–6), grouped by the part of the runner they serve and the interfaces they share:

Running agents in parallel

Ownership

  • One branch and one PR per WP. A WP edits only the files it owns.
  • If a WP needs an interface changed, it opens a small PR against WP0's files and stops. It doesn't edit another WP's module.
  • fakes.py is frozen after WP0. New fakes go in the WP's own test module, and get promoted at WP-INT if two packages use them.

Hardware

  • Wave 1 packages are tested by hand on hardware with overrides, plus any light hardware tests they add (details).
  • Wave 2 is end-to-end bring-up of the whole V2 runner. Fixes go back into the module that owns the failing code.

Merging

  • Wave 1 PRs merge in any order. Each one only fills in stubs.
  • Suggested order if reviewers are short: WP-B, WP-C and WP-D first, since warmup and pooling read their interfaces. Then WP-A, WP-E, WP-F, WP-G and WP-I, then WP-H.
  • Each PR keeps tests/mrv2 under its time budget, and test_layout.py stays green.

Hardware bring-up (Wave 2)

This is the first time V2 is actually hooked up. The hookup is opt-in and off by default:

  • --worker-cls spyre_inference.v1.worker.spyre.worker.SpyreWorkerV2 already works without any code change, because the platform only fills in worker_cls when it's "auto".
  • The engine-wide VLLM_USE_V2_MODEL_RUNNER flag also has to be True, because the scheduler protocol depends on it (report §Triton gate). That needs one small branch in check_and_update_config: when worker_cls points at spyre.worker.SpyreWorkerV2, skip the V1 pin (from #945) and call triton_gate.enable(). This is the only V1-file edit before the flip.

Bring-up runs on x86 with the locked triton-cpu (kernel step 1) and repeats on Power and Z once upstream's replacements are bound (step 2), which is where the step-3 measurements come from. Bring-up order, from the smallest surface to the largest. Each step runs with -W error::torch_spyre.ops.fallbacks.FallbackWarning and, once compiled, SPYRE_COMPILE_GUARD=error:

  1. Decoder, eager, TP1, greedy, head-major KV (a small granite).
  2. Top-k/top-p and logprobs.
  3. Compiled: bucketing, per-block compile, attention recording, zero compiles after warmup with the warmup policy. Expect cold warmup to stay level with V1. Needs vLLM 0.32.
  4. Token-major KV, sliding-window hybrids (gemma), batched decode.
  5. Pooling and encoder-only models: rectangle and ragged plans.
  6. Multimodal, then TP2 and FP8.

Hardware checks the report left open, which get answered in this wave: buf[:n] = x against torch-spyre's self-copy skip (question 4), and whether is_text_generation_model holds for the wrapper (question 8; that one can also be a CPU unit test in WP-G).

The flip PR (Wave 3)

  • Point the platform's default worker_cls at SpyreWorkerV2, and drop the VLLM_USE_V2_MODEL_RUNNER=0 pin and the V1-only rejections.
  • Delete spyre_model_runner.py, the V1 sampler (v1/sample/ and its csrc/ kernels, unless kernel step 3a reused them), SpyreCpuGpuBuffer, the slot-mapping shim and the V1-internal tests.
  • Move-at-flip list: _SpyreModelWrapper → v1/worker/model_wrapper.py; the block-compile helpers → v1/worker/block_compile.py; any subclass in spyre/ that only existed to avoid editing a shared module gets folded back.
  • spyre/ keeps its name, matching upstream's end state where gpu/ stays and the flat V1 files go. Fold SpyreWorkerV2 into spyre_worker.py so that one worker sits outside the package, as gpu_worker.py does upstream. The MRV2-only docstrings stay; the package name still doesn't say it.
  • Update the docs, CLAUDE.md (worker modules, compile notes) and the upgrade-vllm skill.
  • The full CI suite, on hardware, is the acceptance test.

Contingency, unchanged from the report: if V1 is removed upstream before WP-INT is green, hold the pin at 0.31.x or vendor V1 for one release.
