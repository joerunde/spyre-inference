MRV2 bring-up: TP2 and FP8 on hardware

The TP2 and FP8 steps of #1243, run on 9 November 2026 on a two-card Spyre host (x86_64). Every comparison runs the same model and settings once with SPYRE_MODEL_RUNNER=v1 and once with =v2, one engine at a time.

V2 needs no code changes for TP2 or FP8. All 11 V1/V2 engine comparisons are token-exact on every prompt. Every repo e2e test that covers TP2 or FP8 passes on V2 with the compile guard at error. No step fell back to CPU.

One gap remains, and it isn't about correctness. A cold V2 start takes about 3 minutes longer than V1, because MRV2's sampler warmup compiles its full triton-cpu pipeline twice per row width. Cutting that warmup to upstream's CPU path brings V2 level with V1 (199 s against 191 s). Choosing the fix is the follow-up work below.

What was run

  • Code: origin/main at 4178907 (after #1451, #1452 and #1401), unmodified.
  • Stack: vLLM 0.33.0, torch 2.14.1, triton-cpu 3.8.0, torch-spyre fa54674. The RPM bundle is main_snap_2026_11_02_06, installed in user space from spyre-rpms.lock with scripts/install-pinned-rpms.sh --rebuild, because the image's RPMs predate the lock.
  • Hardware: 2 Spyre cards (AIU_WORLD_SIZE=2), PF mode.
  • Every run: a fresh Inductor, vLLM and Triton cache, so each init time is a cold start. SPYRE_COMPILE_GUARD=error on compiled runs and warn on eager ones. FallbackWarning is made an error in every process through a sitecustomize hook (see the note at the end).
  • Engine comparisons: 4 prompts, greedy, 24 new tokens, top-5 logprobs, max_model_len=256, max_num_seqs=4. "Token-exact" means all 96 sampled tokens match. Δlogprob is the largest difference in the chosen token's logprob over those steps.

Findings

A PCIe bus-fence RAS event failed one TP2 test hardware, not V2

In the V2 run of test_distributed_tp2.py, the fifth test, test_tp2_fp8_kv_cache_matches_fp16_cache, failed at engine start. senlib's PCIe monitor thread on TP rank 0 raised RAS::PCI::BusFence (0xa35e, "The card encountered a problem and triggered a PCIe bus fence operation") and aborted the worker. This happened during device init, before any model code ran. It started 8 seconds after the previous test, the 14B multimodal one at TP1 then TP2, had shut down.

Run alone, the same test passed twice on V2 (7.9 min each) and once on V1 (4.7 min). The V1 file run passed it too, and its engine comparison (row "micro-g3.3, TP2, fp16 / fp8" above) is token-exact. I'm treating the failure as a card-reset event that the back-to-back heavy engines made more likely, not a V2 defect. If it comes back in CI, the place to look is the gap between wait_until_card_free returning and the next engine claiming the card.

An fp8 KV cache is not run-to-run deterministic affects V1 and V2

The first TP1 fp8-KV comparison was not token-exact: "Hello, world!" diverged at token 2. That position is a near-tie. In one run the top two candidates were 0.03 nats apart, and in the other they were exactly tied (logprob −3.0768 for both). To tell whether the runner caused it, I ran each runner twice:

PairToken-exactMax Δlogprob
V1 run 1 vs V1 run 2no (prompt 3, token 2)0.1061

V1's second run reproduces V2 bit for bit; V1's first run is the outlier. The same settings with an fp16 cache are bit-stable (Δ ≤ 0.0004), and so is fp8 KV with one sequence at a time. So the noise comes from the fp8 KV path at batch 4, on both runners; it isn't something V2 introduced. In practice it rarely matters, since only exact ties flip, but an exact-token fp8-KV test at a batch above 1 will be flaky. The existing test_fp8_kv_cache.py compares against the fp16 cache with a logprob tolerance, so it isn't affected. Worth a small torch-spyre issue: an fp8 cast or a dequantizing read whose output depends on something other than its inputs.

A cold V2 start takes about 3 minutes longer, all in sampler warmup follow-up

Every compiled V2 run starts 90–185 s slower than V1. The whole difference sits between the LM-head compile and the start of attention recording, a window where V1 spends about 8 s. The fresh Triton cache from those runs shows what fills it. It's MRV2's sampler, compiled through triton-cpu, in two passes per logits row width:

  • The default pass (_gumbel_sample, _bincount, _bias, plus the input-prep kernels) takes about 10 s.
  • The warmup-params pass (SamplingParams.for_sampler_warmup(): penalties, bad words, temperature, min_p, top-k/top-p, logprobs) takes about 80 s per row width. Two compiled row widths cost about 160 s.

Upstream's GPUModelRunner._dummy_sampler_run (vllm/v1/worker/gpu/model_runner.py:1004) skips the second pass when current_platform.is_cpu() is true. Our platform is PlatformEnum.OOT, so is_cpu() is False and we always take both passes. This is a cold-start cost only. One V2 TP2 run whose Triton cache was already warm started in 202 s, against V1's 192 s, so the compiled kernels are reused across runs.

Measured. I reran TP1 compiled micro-g3.3 on V2 with _dummy_sampler_run patched to upstream's CPU branch (default pass only), using a sitecustomize probe and no repo change. The comparison:

Run (cold caches)Cold initWarmupTokens vs V1
V1191 s157 sreference

So the warmup-params pass accounts for the whole gap. That pass exists to compile the penalty, bad-words, min_p and top-k/top-p kernels before serving. Without it, the first request that uses any of those compiles its triton-cpu kernel on the spot. The compile guard watches torch.compile sites, not Triton JITs, so it won't flag that. The probe's greedy requests never reach those kernels, so the probe can't show that cost.

Unexpected compiles in V1 that V2 doesn't have V2 is cleaner

V1 logged vllm/v1/sample/ops/logprobs.py:batched_count_greater_than compiled unexpectedly on its first logprobs request, in both the fp8-KV e2e test and the comparison runs. V2 samples through MRV2's own logprobs kernel, which warmup covers, so it doesn't log this. Both runners log the same 18 unexpected-compile warnings in the eager TP2 test, where the guard is only at warn.

Work required

  1. None for TP2 or FP8 correctness. The TP2 and FP8 rows of #1243's bring-up list can be ticked, and so can the "token-exact against V1" and "no FallbackWarning" criteria, for these models.
  2. V2 cold-start warmup. Decide how to warm MRV2's sampler without paying for the warmup-params pass on every row width. Options:
    • warm the warmup-params pass at one row width only, if the triton-cpu kernels don't specialise on the row count. That's the first thing to check;
    • override _dummy_sampler_run to follow upstream's CPU branch, which was measured level with V1 above, and accept a lazy triton-cpu compile on the first penalised request;
    • rely on a shared Triton cache in deployments.
    The override is a few lines in warmup.py. Until one of these lands, #1243's "cold warmup time is level with V1" criterion isn't met.
  3. CI coverage of V2. The e2e files run V1 unless SPYRE_MODEL_RUNNER is set. Add a V2 leg for test_distributed_tp2.py, test_fp8_kv_cache.py, test_fp8_lm_head_engine.py and the micro-g3.3-fp8 case of test_compile.py, or let #1244's default flip cover it.
  4. Small upstream reports.
    • torch-spyre: fp8 KV-cache nondeterminism at batch > 1, with the two V1 dumps as the reproducer;
    • vLLM: the is_cpu() gate in _dummy_sampler_run should be a platform capability an out-of-tree platform can opt into. Add it to the #1246 workaround table.
  5. Still open in #1243, unrelated to this page: the cold-warmup comparison on larger models, and the whole matrix on Power and Z once #1238 lands.

Method notes

  • FallbackWarning. Neither python -W error::torch_spyre.ops.fallbacks.FallbackWarning nor pytest's -W worked on this host. Python ignores a -W filter whose module isn't imported yet (it logs "Invalid -W option ignored"), and pytest imports torch_spyre while parsing the filter, which fails with a circular import. A sitecustomize.py on PYTHONPATH installs warnings.filterwarnings("error", category=FallbackWarning) once torch_spyre.ops.fallbacks has loaded, in every process: pytest, the EngineCore and both TP workers. No run logged "is falling back to". The -W form in CLAUDE.md and the debug-spyre skill probably has the same problem.
  • Ordering. Every run was sequential, one engine on the cards at a time, V1 first.
  • Not covered. TP4 (this host has 2 cards), larger FP8 checkpoints such as granite-3.3-8b-FP8 (outside this pass's time budget), and spec decode, which V2 refuses (#1575).

Raw dumps (token ids and top-5 logprobs per step), logs and the comparison scripts are kept on the dev pod under the job's run directory, and are available on request.
