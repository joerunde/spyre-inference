PR #1594 V2 vs main V1: host kernels under load

PR #1594 runs Model Runner V2 on C++ host kernels in place of its Triton kernels. Served on gemma-4-26B-A4B at TP2 with the 8k cics trace, V2 is 2.5% slower than main's V1 runner: output throughput −2.5% and mean ITL +2.7%, with TTFT flat (+0.2%). The gap sits inside the decode step, is just past the 2% noise band, and comes from one run per leg.

Throughput, mean TPOT (+2.6%) and mean ITL move together, which is what a longer decode step at fixed concurrency looks like: about 4.5 ms more per step at a step of about 180 ms. Prefill is unaffected: median TTFT is +0.9% and mean TTFT +0.2%. The tail metrics that improve (P99 TTFT −10.4%, P100 ITL −22.5%) are one or two requests each and should be read as noise at n=1. The host kernels were measured at about 0.2% of a step in the earlier spike, so the extra time more likely comes from V2's per-step Python bookkeeping than from the kernels themselves; a per-step host profile of both runners would settle it.

Server startup is measured from the server spawn to the first healthy /health. With a compile cache on it depends on how much of the cache was already populated. Here that is known and lopsided: torch-spyre had just been rebuilt against the pinned RPMs, so the V2 leg compiled everything from scratch and main, running second, reused most of it. The startup rows say nothing about the runners; rerun both legs with SPYRE_KERNEL_CACHE=0, which also sets TORCHINDUCTOR_FORCE_DISABLE_CACHES=1 and VLLM_DISABLE_COMPILE_CACHE=1, to measure them. The startup and compilation rows come from _server.log, as the max across TP workers. Total compilation is the wall time of the whole Spyre warmup. V2's warmup logs its dummy runs in a different line (MRV2 warmup: 4 dummy runs [512, 4, 2, 1]) that the collector does not parse, hence the dashes. Δ colours: green better, black within ±2%, orange 2–10% worse, red more than 10% worse.

Caveats

  • One run per leg (n=1). The 2.5% decode gap is just outside the ±2% band, so it needs a repeat (or a second shape) before it is treated as a settled number.
  • Both legs exceed the 1.1 ITL mean/median flag, by about the same amount. Neither server log has a single compiled unexpectedly warning, so the skew is not compilation inside the window; it matches 512-token prefill chunks of the long cics prompts landing in a running batch, which both runners do the same way.
  • Startup and compilation are not comparable between legs (see above): V2 ran first on a cold kernel cache, and main reused it.
  • The V2 leg's first attempt never started: the venv's torch-spyre had been built against the pod image's older runtime, not the pinned RPMs, and failed to import under ~/spyre-libs/env.sh. torch-spyre was rebuilt against the pinned RPMs and both legs ran on that build.
  • One shape only: TP2 is the most this pod's two cards allow, and larger batches, where per-step host work matters more, were not run.
