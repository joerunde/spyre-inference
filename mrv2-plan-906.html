Model Runner V2: implementation plan

Follow-on to the investigation report for #906. The report covers what an MRV2 runner needs; this page covers how we build it. · 2026-10-09 · against spyre-inference ad76a00 (main pins vLLM v0.28.0; #945 to v0.31.0 is still open).

TL;DR

  • Build it beside V1. All new code goes in a new package, spyre_inference/v1/worker/mrv2/. No V1 module imports it. Importing it has no side effects. The platform still picks TorchSpyreWorker. V1 files are not edited until the flip PR, with one small exception in the bring-up phase.
  • Small files, one job each. About 25 files that mirror upstream's vllm/v1/worker/gpu/ layout, with a soft cap of 300 lines and a hard cap of 400, enforced by a test. model_runner.py stays a thin coordinator that hands each concern to a component module.
  • Kernels come from upstream. The Arm CPU maintainer is preparing a PR that moves every non-Triton CPU backend to MRV2, with torch and C++ kernels (vllm#55847 thread, 2026-10-09). We write a single seam module, kernels.py, and no kernels of our own. Until upstream lands, we vendor its kernels, or use triton-cpu on x86 dev hosts only. Two risks to raise upstream now: we build vLLM with VLLM_TARGET_DEVICE=empty, so there is no _C, and our platform is OOT, so is_cpu() is False.
  • Small CI cost. New tests live in tests/mrv2/. They run on CPU with fakes, and a conftest guard fails any test that loads a model, calls torch.compile or touches the Spyre device. The whole directory should finish in about 20 s. Real coverage arrives with the flip PR, when the existing suites run on V2. We don't parametrize the suites over v1|v2, because that would double CI.
  • Four waves. Wave 0 is one serial skeleton PR that fixes the files, class stubs and interfaces. Wave 1 is nine work packages that run in parallel, each owning its own files and tests. Wave 2 is serial bring-up on one Spyre card. Wave 3 is the flip.

Ground rules

Each of the five constraints becomes a rule we can check in review or with a test.

1 · Don't disrupt existing work

  • New code only goes under spyre_inference/v1/worker/mrv2/ and tests/mrv2/.
  • Nothing outside mrv2/ imports it. A test walks the AST of every module in spyre_inference/ and checks this.
  • Importing the package does nothing. The torch.cuda placeholders, the Triton-gate patch and the kernel registration run only from the V2 worker's init_device.
  • pyproject.toml and uv.lock don't change. Triton stays banned.
  • If a shared helper doesn't fit, we subclass or wrap it inside mrv2/ and leave the original alone. Each case goes on the move-at-flip list.

2 · Don't blow up CI time

  • Tests run on CPU only and use hand-built fakes, with no LLM(...), no HF downloads and no subprocess engine.
  • An autouse fixture in tests/mrv2/conftest.py makes torch.compile, vllm.LLM.__init__ and torch_spyre device allocation raise.
  • Budget: under 1 s per test and about 20 s for the directory. A session-finish hook fails the run when the total goes over.
  • These tests are unmarked, so they run in the smoke shards, which run them anyway.

3 · Plan for parallel work

  • Wave 0 writes every file, with real signatures and NotImplementedError bodies.
  • Each Wave 1 package owns a disjoint set of files: its source files and its test files.
  • model_runner.py, worker.py and the shared fakes belong to Wave 0 and Wave 2, not to Wave 1 packages.
  • Wave 1 never touches the Spyre card, so any number of agents can run at once.

4 · Get the encapsulation right

  • The layout mirrors upstream gpu/: every Spyre file maps to the upstream file it extends.
  • Files soft-cap at 300 lines and hard-cap at 400, enforced by tests/mrv2/test_layout.py.
  • Per-step encoder state moves off the runner and onto the model state, where MRV2 expects it.
  • Imports point one way: components → shared Spyre modules → vLLM. Components never import model_runner.py.

5 · Kernels come from upstream

  • All kernel binding goes through one module, mrv2/kernels.py.
  • Sources in order of preference: what upstream registers, then a vendored copy (with its SHA recorded) until it reaches our pin, then triton-cpu on x86, for local dev only.
  • A coverage test lists every default-path @triton.jit kernel and fails when one of them has no binding.

Version targeting

MRV2's API moves between releases, and the pieces we need land in different versions:

vLLMWhat it gives the V2 packageConsequence

0.31 (#945)Triton kernel dispatcher (register_triton_kernel_overrides), NonUvaBuffer.The kernel seam needs this. Wave 1 packages develop against it.

Rule: the package builds against whatever main pins. Version-specific code lives in the one module that needs it, behind one vllm_version >= … check. We don't scatter try/except ImportError through the package. An import smoke test (tests/mrv2/test_imports.py) catches upstream renames on every bump. The upgrade-vllm skill should add "run tests/mrv2" to its checklist.

What model_runner.py looks like

Wave 0 writes this in full. Wave 1 packages fill in the modules it calls and leave it alone.

class SpyreModelRunnerV2(GPUModelRunner):
    def __init__(self, vllm_config, device):
        super().__init__(vllm_config, torch.device("cpu"))
        self.spyre_device = device

    def load_model(self, *args, **kwargs):
        load.load_and_wrap(self, *args, **kwargs)        # load.py, compile.py

    def initialize_kv_cache(self, kv_cache_config, **kwargs):
        attn_groups.init(self, kv_cache_config)          # attn_groups.py
        kv_cache.init(self, kv_cache_config, **kwargs)   # kv_cache.py, block_table.py
        self.cudagraph_manager = bucketing.SpyreBucketManager.from_runner(self)

    def pool(self, *args, **kwargs):
        return pool_output.pool_sync(self, *args, **kwargs)  # pool/output.py

    def warming_up_model(self):
        warmup.run(self)                                 # warmup.py

Reuse vs. V2-local

Everything below the runner is shared with V1: attention, custom ops, bucketers, compile guard and the pooler heads. The V2 package imports these modules as they are. It doesn't copy them, and it doesn't refactor them before the flip.

PieceLives inV2 uses it
Attention backends, kernels, SpyreAttnBucketerv1/attention/as is Every field the metadata builder reads is still passed (report §A5).
SpyreShapeBucketer, compile_guardv1/worker/as is bucketing.py and warmup.py call them.
Pooler heads and patches (spyre_pooler.py)v1/pool/as is except copy_pooler_output_to_cpu, which imports a private V1 symbol. V2 has its own copy in pool/output.py.
Custom ops, models, multimodal patches, communicatorelsewhereas is
_SpyreModelWrapper, compile helpers (_repeated_block_lists, _compile_granularity, …)spyre_model_runner.py (module level)import them as they are. If the wrapper needs a V2 change (the mm staging buffer), subclass it in mm/.
Runner methods (_preprocess, _pool, _build_attention_metadata, …)TorchSpyreModelRunnerport into the component that owns that logic now. We don't inherit from the V1 runner.

A V2 module importing private names from spyre_model_runner.py is the one deliberate coupling. It's acceptable because V1 never changes because of it, and the flip PR moves those helpers to a shared module (v1/worker/model_wrapper.py, v1/worker/block_compile.py) with git mv. Doing that move now would conflict with every open PR that touches the runner.

Kernel strategy

Update since the report: the report recommended writing our own pure numpy/torch kernels. That's no longer needed. On vllm#55847, fadara01 (Arm) said on 2026-10-09 that they are "preparing a PR to migrate all non triton CPU backends to MRv2, including Arm, RiscV, ppc64le, etc.", with C++ kernels where the torch version is too slow, and will ping us to test on IBM hardware. #58140 already installs prebuilt triton-cpu on x86_64.

So the kernel work becomes a binding problem, handled in kernels.py:

  1. Upstream-registered. Once upstream's fallbacks reach our pin, kernels.bind() checks they're registered for our platform, and registers them if they're keyed on CpuPlatform.
  2. Vendored. Before then, copy the upstream PR's torch kernel files into mrv2/_vendored/ unchanged, with the source SHA in the header, and register them through the v0.31 dispatcher. Delete them at the bump that brings them in.
  3. triton-cpu, x86 dev hosts only. Install it with uv pip install into a dev venv and run with uv run --no-sync. vLLM only accepts Triton's CPU backend when its version string contains cpu, so triton_gate.py has a dev-only switch for that check too. This never goes into the lockfile or CI, and doesn't run on Power or Z.

Raise these on the upstream PR now, before it's written around our blind spots:

  • No _C. We build vLLM with VLLM_TARGET_DEVICE=empty. Every C++ kernel needs a pure-torch fallback that stays registered when _C is missing.
  • Gate on capability, not on is_cpu(). Our _enum is OOT. If the fallbacks or the Triton-gate exemption are keyed on current_platform.is_cpu(), we're shut out. Ask for a platform capability (as #57684 asks), or make the registration reusable from an OOT platform.
  • s390x is big-endian. Offer Z hardware for testing, along with ppc64le.
  • Scope. We also need the sampler kernels (gumbel/temperature, logprobs, penalties, min_p, bias, bad_words), not only input prep. Check they're included.

The coverage test (tests/mrv2/test_kernel_coverage.py) imports the MRV2 modules, lists every @triton.jit on the default path and fails when kernels.py has no binding for one. It's a pure import-and-inspect test, and it's what catches a renamed kernel after a bump.

Interfaces WP0 has to settle

These are the only cross-package contracts. If they're right in WP0, Wave 1 packages never need to edit each other's files.

  • bucketing.SpyreBucketManager.from_runner(runner) and .bucket(num_tokens) -> int. Warmup enumerates through this.
  • encoder_plan.EncoderPlan: a dataclass for the per-step plan (rectangle/ragged, grid, rows), set by D, read by F and H.
  • kv_cache.init(runner, cfg, **kw) and attn_groups.init(runner, cfg), plus the attribute names they set on the runner (attn_groups, kv_caches).
  • load.load_and_wrap(runner): postcondition is that runner.model is the wrapper and every holder points at it.
  • kernels.bind() -> set[str] and DEFAULT_PATH_KERNELS.
  • warmup.plan(runner) -> list[DummyCall] kept apart from warmup.run(runner), so the plan can be tested without running anything.

Running agents in parallel

Ownership

  • One branch and one PR per WP. A WP edits only the files it owns.
  • If a WP needs an interface changed, it opens a small PR against WP0's files and stops. It doesn't edit another WP's module.
  • fakes.py is frozen after WP0. New fakes go in the WP's own test module, and get promoted at WP-INT if two packages use them.

Hardware

  • Wave 1 agents don't need the card, and their tests can't touch it because of the conftest guard.
  • Wave 2 runs one process on one card at a time (CLAUDE.md: never two Spyre commands at once). One agent or person drives bring-up.
  • Agents can make code fixes for bring-up failures in parallel, but hardware reruns happen one after another.

Merging

  • Wave 1 PRs merge in any order. Each one only fills in stubs.
  • Suggested order if reviewers are short: B, C, D first, since warmup and pooling read their interfaces. Then A, E, F, G, I, then H.
  • Each PR keeps tests/mrv2 under its time budget, and test_layout.py stays green.

Hardware bring-up (Wave 2)

This is the first time V2 is actually hooked up. The hookup is opt-in and off by default:

  • --worker-cls spyre_inference.v1.worker.mrv2.worker.SpyreWorkerV2 already works without any code change, because the platform only fills in worker_cls when it's "auto".
  • The engine-wide VLLM_USE_V2_MODEL_RUNNER flag also has to be True, because the scheduler protocol depends on it (report §Triton gate). That needs one small branch in check_and_update_config: when worker_cls points into mrv2, skip the V1 pin (from #945) and call triton_gate.enable(). This is the only V1-file edit before the flip.

Bring-up order, from the smallest surface to the largest. Each step runs with -W error::torch_spyre.ops.fallbacks.FallbackWarning and, once compiled, SPYRE_COMPILE_GUARD=error:

  1. Decoder, eager, TP1, greedy, head-major KV (a small granite).
  2. Top-k/top-p and logprobs.
  3. Compiled: bucketing, per-block compile, attention recording, zero compiles after warmup. Needs vLLM 0.32.
  4. Token-major KV, sliding-window hybrids (gemma), batched decode.
  5. Pooling and encoder-only models: rectangle and ragged plans.
  6. Multimodal, then TP2 and FP8.

Hardware checks the report left open, which get answered in this wave: MRV2 dummy runs against the recorded attention variants (question 5), buf[:n] = x against torch-spyre's self-copy skip (question 4), and whether is_text_generation_model holds for the wrapper (question 8; that one can also be a CPU unit test in WP-G).

The flip PR (Wave 3)

  • Point the platform's default worker_cls at SpyreWorkerV2, and drop the VLLM_USE_V2_MODEL_RUNNER=0 pin and the V1-only rejections.
  • Delete spyre_model_runner.py, v1/sample/topk_topp_sampler.py, SpyreCpuGpuBuffer, the slot-mapping shim and the V1-internal tests.
  • Move-at-flip list: _SpyreModelWrapper → v1/worker/model_wrapper.py; the block-compile helpers → v1/worker/block_compile.py; any subclass in mrv2/ that only existed to avoid editing a shared module gets folded back.
  • Decide whether mrv2/ keeps its name or becomes the worker package. Renaming it is a plain git mv, since nothing outside imports it.
  • Update the docs, CLAUDE.md (worker modules, compile notes) and the upgrade-vllm skill.
  • The full CI suite, on hardware, is the acceptance test.

Contingency, unchanged from the report: if V1 is removed upstream before WP-INT is green, hold the pin at 0.31.x or vendor V1 for one release.
